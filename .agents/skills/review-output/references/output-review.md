# 文章の明確さと説明の重複の確認

## PRコメントの返信状況

自分のPRのコメント調査・対応可否の判断、未返信コメントの報告、対応の着手、返信案の作成に先立ち、対象PRの全コメントと返信履歴を照合する。

1. 通常コメント、レビュー本文、インラインコメントとその返信を全ページ取得する。日付・現在の差分・未解決状態で取得対象を絞らず、全返信を取得する前に元コメントだけを抽出しない。GraphQLではスレッド一覧と各スレッド内のコメントの両方のページ送りを確認する。
2. インラインはコメントIDと`in_reply_to_id`、またはスレッド内の全コメントで本人の返信を対応付ける。通常コメントやレビュー本文にある引用・元コメントURL・同じ論点への回答も照合する。別投稿で回答されていれば返信済みとする。
3. 本人が返信した日時・URL・判断を候補ごとに確認する。本人の返信後に新しい質問や追加の対応依頼があれば、その追加部分の返信要否を判定する。後続コメントがあるだけで、元の指摘全体を未返信へ戻さない。
4. 返信済み、スレッド解決済み、コード対応済みを区別する。古いコミットへの指摘やoutdated表示でも返信履歴は有効である。現行diffに問題が残る場合は、返信済みの指摘に対する実装上の残件として扱い、未返信と呼ばず、重複する返信案を作らない。
5. 未返信と報告する候補ごとに、元コメントのURLと、本人の返信がないと判断した照合範囲を確認する。botの通知・自動要約は、返信を必要とする質問・指摘かを判定する。返信を求めないCI通知はCIの状態として扱う。
6. 提示直前に追加のコメント・返信を再取得し、回答済みの候補を除く。ページ取得の失敗や本文の省略が残る場合は返信状況を未確認とし、未返信や「未返信コメントなし」と断定しない。
7. 取得した指摘をコメントIDごとに、対応済み・未対応・不採用・判断保留へ整理する。自動レビューのジョブ成功やCI成功を、指摘への対応完了とみなさない。対応可否の判断を依頼された場合は、各指摘への判断と根拠を元コメントへのリンクとともに示す。

### PR作成・更新後の完了報告

- 完了報告の直前にHEAD、CI、自動レビューの実行状態を再取得し、上の手順でコメントと返信を照合する。以前の取得結果だけでレビューを実行中・完了と報告しない。
- 未対応・判断保留の指摘と実行中のレビューは、元コメントや実行へのリンクを添えて完了報告に残す。別のPRへ作業を移す場合も、元PRの残件を引き継ぐ。今回の依頼範囲で対応しない指摘は、その判断を明示する。

## 主述・対象・修飾の確認

応答を送信する前と文書を保存する前に、見出し・表・箇条書きを含む本文全体を確認する。文章を短縮した場合は、短縮後の文を読み直す。

- 主語と述語が意味の上で対応しているか確認する。動作を述べる文では、誰が何をどうするのかを読み取れる形にする。文脈から一意に分かる主語は省略してよい。
- 作成・更新・確認・適用などの動作には対象を示す。見出しや直前の文から対象を一意に特定できなければ補う。短くするために必要な対象を省かない。
- 修飾語は、何を限定・説明するかを明確にし、修飾する語の近くへ置く。複数の解釈ができる場合は語順を変えるか文を分ける。読み手の推測が必要な名詞の連結を避ける。
- 複数の語を並べた文では、共通の述語・修飾語が各項目に成立するか確認する。成立しない項目は別の文に分ける。

例: 「作成・編集時の配置はスキルに従う」では対象が曖昧になる。「AGENTS.md・スキル・hookを作成・編集するときは、指定のスキルに従う」と書く。

## 説明先をまたぐ重複チェック

PR説明・コメント・ドキュメント・Notionを書く前と送信前に、次を確認する。短文にも適用する。

1. 依頼に関係するdiff（docsの変更を含む）、既存の本文・コメント・参照文書を読み、同じ論点の説明先を確認する。Notionの取得は、Notion操作を明示された場合に限る。取得できない資料を確認済みと扱わない。
2. 各説明について、既存の記述や参照リンクだけでは読み手のどの判断ができないかを確かめる。答えがなければ加筆しない。言い換え・短縮・別見出しへの移動も、情報が増えなければ重複である。設計判断・提供範囲・互換性・認証の前提・権限制約という分類だけを再掲の理由にしない。
3. 仕様・理由・手順の詳しい説明は、その情報を継続して読む場所に置く。他の場所には必要なリンクと未説明の判断材料だけを書く。PR本文・コメント・docs・Notionをそれぞれ完結させるために同じ説明を複製しない。必須テンプレートには必要最小限の回答や参照を置き、詳しい説明は参照先に集約する。
4. 下書きを参照元と照合し、繰り返した段落・表・チェックリストを除く。トグルや作業ログへ移すだけでは解消にならない。既存資料の整理は依頼の範囲内に限り、過去の判断・リンク・記録を失わせない。

### PR説明の粒度の例

公式GitHub MCP Serverの採用を説明する際、`--read-only`、公開toolの選択、不正なアクセスモードの拒否、リポジトリ・パス・コミットSHA・返却量の検査をPR本文へ列挙しない。実装とテストで確認する動作である。

採用理由や読み取り専用の提供範囲も、docsのdiffやコメントにあれば再掲しない。「保守を減らすため公式MCPを採用し、今回は読み取り専用とする」と短縮しても重複は残る。未説明でレビュー前に必要な判断材料がある場合だけ、その点を補う。安全性を説明したいという書き手の都合で段落を増やさない。

秘密鍵のSecret Managerへの保存、Agent IdentityへのSecret単位の読み取りIAM付与は設定手順の説明先に置く。専用デプロイSAでもRuntimeや共通バケットの権限を完全には分離しないという既存制約も、docsにあればPRへ転記しない。GitHub未設定時の従来動作についても、「互換性はPRに残す意味がある」と自動的に残さない。「任意機能で既存利用者の追加設定は不要」と短縮する前に、すでに説明済みかを確認する。指摘された段落を削るとき、代わりの要約文を必ず残す必要はない。
