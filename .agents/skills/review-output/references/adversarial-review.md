# 長文成果物の独立レビュー

## 長文アウトプットの敵対的チェック（sub-agent起動）

数行を超える成果物を送る前に、次の手順を行う。対象はPR説明・Issue/PRコメント・Slack投稿・Notionカードに限らず、plan file・調査ログ・技術文書など任意のドキュメントを含む。数行程度の短い応答には適用しない。

1. 下書きを確定させた後、haiku等の軽量モデルでsub-agentを1つ起動する。**会話上の経緯・意図・自己評価は渡さず、下書きと重複照合に必要な既存本文・diff・コメント・参照文書を渡す。** 該当箇所だけを抜き出して送らない。抜粋を送ると、書き手が「ここが怪しい」と選んだ箇所にsub-agentの注意が引きずられ、バイアスがかかる。全文をそのまま読ませ、どこに問題があるかはsub-agent自身に見つけさせる
   - ファイルが新規作成、またはサイズが小さくsub-agentのコンテキストに収まる場合はファイル全体を渡す
   - 既存ファイルへの追記・修正で全文が大きすぎる場合は、diffを取り、変更箇所ごとに前後5行を含めて渡す。変更のあった段落だけを渡すのではなく、diff全体を対象にする
   - プロンプトには本文に加えて「これは読み手（レビュワー・チームメンバー・将来の自分）が判断・理解するのに本当に必要な情報だけか。てにをはなど細部だけでなく、章立て・論理の流れ・重複・話の飛躍など全体を通しての構成もメタ認知的に見て、読み手にとって不要な説明・背景・経緯・試行錯誤・繰り返し・構成上の問題を具体的に指摘してほしい」という趣旨の指示を渡す。あわせて「英語の技術用語を字句単位でそのまま漢字の熟語に置き換えた不自然な訳語（カルク・翻訳借用）が無いか、実際にその意味でIT用語辞典・技術文書に使われている語かどうかも確認してほしい」という観点、および「文中に、作業の進め方・分担・執筆方針そのものを宣言する文（誰が書く・決める、一案に絞らないといった運用ルールの引用）が紛れていないか」という観点も加える
   - 文書内の重複に加え、他の説明先ですでに足りている内容と、実装を言い直した説明を指摘させる。判定には「説明先をまたぐ重複チェック」を使う。
2. 返ってきた指摘を確認し、妥当なら該当箇所を削るか必要な参照に置き換える。重複を短く言い換えて残さない。構成上の指摘であれば章の統合・順序の入れ替えも検討する。書き手側の都合（コンテキストを渡された以上書きたい）を優先せず、読み手が必要とする範囲に絞る
3. 指摘を反映しない場合は、その理由を自分の中で明確にしてから残す。理由なく無視しない

この手順は、文章表現を担当するyomiyasuの確認や、技術文書で明示された表記規約の確認に追加して行う。
