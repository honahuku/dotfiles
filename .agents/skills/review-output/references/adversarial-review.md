# 長文成果物の独立レビュー

数行を超える成果物を送る前に、独立したレビューを行う。対象はPR説明・Issue/PRコメント・Slack投稿・Notionカードに限らず、plan file・調査ログ・技術文書など任意のドキュメントを含む。数行程度の短い応答には適用しない。

## 通常の独立レビュー

1. 下書きを確定させた後、新しいsub-agentを1つ起動する。会話履歴を引き継ぐ既存のsub-agentは使い回さない。利用可能ならhaiku等の軽量モデルを選ぶ。
2. 下書き全文と、重複や参照先を照合するために必要な既存本文・diff・コメント・参照文書を渡す。会話上の経緯・意図・自己評価は渡さない。該当箇所だけを抜き出して送らない。新規または小さなファイルは全文を渡し、既存ファイルが大きい場合はdiff全体と、変更箇所ごとの前後5行を渡す。
3. 読み手に本当に必要な情報かを全体から評価させ、章立て・論理の流れ・重複・話の飛躍・不要な背景や経緯・試行錯誤・反復を具体的に指摘させる。文書内だけでなく他の説明先にある説明や、実装の言い直しも確認させる。判定には`output-review.md`の「説明先をまたぐ重複チェック」を使う。
4. 技術用語が実際に含まれる場合は、不自然な直訳や実用されていない訳語がないかも確認させる。文書に書き手の試行錯誤や執筆上の都合を説明する記述が紛れていないか確認させる。ただし、内容の理解に必要な担当範囲・役割・判断主体は削除候補にせず、未確定の値は該当箇所の記入欄やTODOとして保つ。

## 共有資料の独立読者レビュー

共有先の読者が本文だけで内容を理解できるかを確認する場合や、旧資料を置き換える場合は、通常レビューと別の独立読者レビューを行う。

- 新しいsub-agentへ渡すのは、下書き全文、想定読者、用途、今回確認する要件に必要な最小限の情報だけとする。会話履歴、書き手の説明・自己評価・試行錯誤、旧資料、リンク先、調査メモ、コメントは渡さない。旧資料を知らない読者としてレビューさせる。
- 章立て、前提不足、リンク先への依存、主語・役割の曖昧さ、矛盾、不要な経緯や反復を、該当箇所を選別せず本文全体から探させる。
- 空欄やTODOは、値が未確定という理由だけで欠陥としない。評価方法を作る草案・記入式テンプレートと、実測結果・確定事項を報告する文書を区別し、未知の担当者・数値・合意を創作させない。読者に必要な役割・判断主体の説明は保ち、未確定なら該当箇所にTODOを置く。
- 事実・出典の照合が必要な場合は、読者レビューとは別に行い、その確認に必要な根拠資料を渡す。根拠を見せない読者レビューだけで事実確認や実現可能性の確認まで完了したと扱わない。

レビュー後は、指摘の妥当性を根拠と照合する。妥当な指摘は該当箇所の削除・必要な参照への置き換え・章の統合や順序変更で反映する。重複を短く言い換えて残さない。採用しない指摘には理由を明確にする。
