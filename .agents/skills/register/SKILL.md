タスクを登録する。

不在・早上がりに伴う退勤予定の登録は[check-kintai](../check-kintai/SKILL.md)の「フレックス退勤予定の登録」を使う。通常タスクへ変換しない。

ユーザのタスク内容(自然文): $ARGUMENTS

入力が空なら、何を登録するかを1行で尋ねる。

## 手順

1. $ARGUMENTS からタイトル・due（明示された場合のみ）・タグ（`#tag`）を抽出する。**Slack / Notion などのリンクが含まれていたら、確認を取らずにリンク先を読みに行ってタイトルを具体化する。** リンクを貼った時点でタイトル具体化に使ってよいという意図がある。
2. **`from` を決める**。有効値は `others` / `me` の2択のみ。「外部から要求が来ているか」で判断する。
   - `input-kousuu` スキルを指定して工数を入力するタスク、またはタイトルが「工数入力」のタスクは、業務上の依頼として `others` にする。`input-kousuu` スキル自体の改善・調査タスクはこの例外に含めず、下記の一般ルールで判断する
   - `others`: 他者から依頼された・締め切りがある・やらないと誰かに影響が出る（PR レビュー依頼・Reviewee 対応・障害対応・期限付き申請など）
   - `me`: 自分が「やりたい」と思って立てた・やらなくても外部に影響が出ない（調査・学習・自発的な改善など）
   - 判断できない場合のみ ユーザーへの確認 で1問だけ聞く: options は `others`（外から）/ `me`（自分で）の2択
3. 保存先を決める。
   - デフォルト → **ローカル**。確認不要で保存する
   - "GitHubに" / "Issueにして" → GitHub Issue を作成。`meta.default_github_repo` が設定済みならそれを使う。未設定なら1回だけ聞いて保存する。`gh issue create --repo <owner>/<repo> --title "..." --body "..."` で作成。**実行前に確認する**
   - "Notionに" → `meta.notion_tasks_db` の Notion DB にページを作成。未設定なら1回だけ聞く。**実行前に確認する**
4. 保存: `tasks add "<title>" --from <others|me> [--due <YYYY-MM-DD>] [--source ...] [--source-url ...]`
   - `queue_pos` は指定しない（末尾追加がデフォルト）
5. 外部サービスに作成した場合は、ローカルにもスタブを登録する: `--source github|notion --source-url <url>`

完了後はタスク id とタイトルだけ返す。登録内容を長々と復唱しない。

## タイトルの形式

PR に関連するタスクは `<一言概要> (<リポジトリ名> #<番号>)` の形式にする。PR 番号だけにしない。
- 一言概要は PR タイトルをそのまま使わず、日本語で何の PR か分かる粒度で書く
- 反例: `example-actions PR #193 マージ・リリース告知`
- 良い例: `deploy.yml キャッシュ制御 inputs 追加 (example-actions #193) マージ・リリース告知`
- 反例: `PR #2079 レビュー (Reviewer)`
- 良い例: `IAP アクセスメンバーコントローラー追加 (example-app #2079) — レビュー (Reviewer)`

## しないこと

- 外部サービス（GitHub / Notion）への書き込みを確認なしで実行しない
- `from` が不明でも1問しか聞かない
- `due` を聞かない（ユーザーが言ってきたときだけ入れる）
- タスク内容を推測で補完しない（不明なら1文で確認する）
- `--layer` / `--importance` フラグを tasks コマンドに渡さない（廃止済み）
- `review` / `action` / `info` などの無効な値を `from` に渡さない
