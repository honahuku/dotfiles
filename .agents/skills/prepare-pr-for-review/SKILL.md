# PRを作成・更新し、レビューに備える

自分が作者のPRを新規作成するとき、本文を更新するとき、レビューに出せる状態か確認するときに使う。draft PRの作成も対象とする。他人のPRをレビューするときは`review`を使う。

## 読み込むタイミング

draftを含むPR作成・本文の作成や更新を依頼されたら、説明を書き始める前に読む。PRの作成・本文更新の直前には「PR説明のセルフレビュー」と「PR / Issue への書き込み前の確認」を適用する。

## draft解除の実行条件

- このスキルの実行は、仕上げと確認結果の報告までとする。確認項目を満たしても、PRのdraftは解除しない。
- draft解除は原則としてユーザーが操作する。例外は、同じセッションで「Readyにして」「openにして」など、draft解除を明示的に依頼された場合だけである。その場合はCoding Agentsが実行してよい。
- 「レビューに出せるか確認して」「仕上げて」や、スキルの呼び出しはdraft解除の依頼に含めない。過去のセッションの許可も使わない。
- 明示的な依頼がない限り、`gh pr ready`、API・MCPのdraft解除、サブエージェントへの委譲など、どの手段でもReady化しない。
- 確認結果は、レビューに出せる状態かと、残る未確認事項を短く報告する。PRの状態変更とは区別する。

## PR説明を書く前に

不要な長文や、説明済みの内容を複数箇所に繰り返し書くことは、依頼者だけでなくレビュアーや文書の読者の時間を奪う最低な行為である。読む・照合する・重複だと見分ける負担を相手に押し付けるため、単なる文体の好みとして扱わず、繰り返してはならない。
そのため、docsのdiffやコメントで足りる説明をPR本文に再作成しない。本文を単独で完結させるために長くせず、参照と未説明の判断材料だけを残してセルフレビューする。

`write-technical-docs`の`references/technical-writing.md`にある「文体と簡潔さ」「変更の理由と技術的な認識」を読む。同資料の「ファイルの差分と実際の影響を分ける」に従い、編集していない参照元への影響も確認する。

テンプレートの探索と本文の構成は、`write-technical-docs`の`references/pr-writing.md`「PR説明の構成」に従う。

執筆前と送信前に`review-output`の「説明先をまたぐ重複チェック」を行う。

## コミット整理

**draft 解除をユーザーに促す前に、コミット整理を検討する。** 試行錯誤・レビュー指摘対応で積み上がった複数コミットは、レビュアーには不要な履歴になっていることが多い。1機能の完成形として1コミットにまとめられないか確認する。

実際の整理手順と操作前の確認は、`apply-git-strategy`の`references/commit.md`「コミットの整理」に従う。

コミット整理と同時に、次の管理元に従って書き分けを再確認する。

- コード・テスト・コードコメント：`write-safe-code-and-scripts`の`references/code-validation.md`。
- コミットメッセージ：`apply-git-strategy`の`references/naming.md`。
- PR説明の重複・試行錯誤の記載・Test plan：以下の「PR説明のセルフレビュー」。

## PR説明のセルフレビュー

draftを含むPR作成・本文更新・Ready化前に、次の項目を確認する。不足があれば反映前に直す。

1. テンプレートを確認し、その構成と必須項目を満たしているか。
2. diffと参照先を含めて、問題と変更の目的が分かるか。
3. diffと参照先を含めて、変更の理由と影響を判断できるか。チーム・ロール・参照先の変更では既存の参照元も確認したか。未説明の判断材料だけを補い、実装の動作や安全性を本文に列挙していないか。分からない理由を作っていないか。
4. 対象外の説明がレビュー判断に必要な場合、その範囲と根拠が分かるか。ファイルに差分がないことを、実際の影響がないことと混同していないか。不要な対象外の説明を作り足していないか。
5. `write-technical-docs`の`references/technical-writing.md`「文体と簡潔さ」と、`review-output`の主述・修飾語の確認を完了したか。
6. `review-output`の「説明先をまたぐ重複チェック」を完了したか。試行錯誤や執筆方針の宣言も除いたか。
7. 根拠を一次情報で確認したか。仕様・設計判断の出典は該当箇所の近くに置く。コードの参照はコミットSHAと行番号で固定する。ログは再現可能な検索クエリで示す。
8. 関連PRは番号と短い要約を添え、分割PRは相互に参照できるか。Slack・Notion・Issueなどは、生のIDではなく内容が分かるリンクにしたか。
9. Test planはリポジトリで定められた項目・CI結果に限り、確認済みと未確認を区別したか。観測する応答と確認できる範囲を照合し、技術的な認識の訂正を関連する説明・確認条件にも反映したか。

### 分量の判断

残す情報は短い段落か必要最小限の箇条書きにする。参照先で足りる説明は、本文に残す項目の対象にしない。

行数制限のために要点を隠したり、一文へ詰め込んだりしない。長ければ重複と不要な説明を削り、詳細な仕様・手順は既存文書へリンクする。トグルは、本文に残す必要がある補足資料だけに使う。トグル内を含めて全文の簡潔さを確認する。

### Test planの扱い

- PRテンプレート・CONTRIBUTING・CI・必須手順で定められた項目またはCI結果だけを書く。個人の文章校正・秘密情報検出・補助lintは、リポジトリで必須とされていない限り載せない。
- 実行可能な必須確認を行い、結果と期待する挙動を照合する。確認済みは`- [x]`、未確認は`- [ ]`にする。残る確認は未確認事項という説明だけで済ませず、何を確認すれば完了か分かる項目にする。想定外の差分や失敗を成功扱いにしない。
- merge後の確認が必要な場合だけ、Test plan内でmerge前後を区別する。不要な確認欄は作らない。
- Terraform・Kubernetes manifestでは`write-safe-code-and-scripts`のインフラ検証手順を適用し、必要な検査が対象head・環境でCI実行され完了したことを確認する。禁止CLIの結果を取得できなければ、別手段や未確認チェック欄だけで済ませず停止して判断を仰ぐ。workflowの実装からapply・デプロイのトリガーも確認し、それらを起動するmerge・push・rerun・承認は実行しない。

### Notionカードを扱う場合

PRの構成をそのまま転用せず、カードの既存構成に沿う。執筆前と送信前の重複チェックは作業ログにも適用する。展開部は見出しを除いて実質5ブロック以内とし、段落は2〜3文までにする。空の見出しは残さない。

5ブロックに収めにくい場合は、実装粒度のタスクか親タスクかを判断し、To doの粒度を確認してから起票する。機械的に分割しない。プロジェクトのバックログの起票・更新は`edit-project-backlog`に従う。

## PR / Issue への書き込み前の確認（重複チェック・上書き前取得）

**書き込みの主体を対象で分ける。**

- **PR / Issue のコメント投稿・返信**（`gh pr comment` / `gh api` での issue・review コメント / Slack 送信など）: Coding Agentsから投稿しない。どんな場合もユーザーが一度必ず内容を確認してから、ユーザー自身が投稿する。返信案をプレビューとして見せるところまでにする。
- **PR本文の更新**（`gh pr edit --body`）: 本文更新が依頼の範囲に含まれ、上記セルフレビューを満たせば反映してよい。行数だけで可否を判断しない。

**`gh pr edit`・`gh pr comment`・`gh api .../comments` 等を実行する前に必ず行う手順:**

- 最新の PR / Issue 状態を取得してから書き込む
  - 取得例: `gh pr view <N> --json body`, `gh api --method GET repos/<owner>/<repo>/issues/<N>/comments`, `gh api --method GET repos/<owner>/<repo>/pulls/<N>/comments`
- `gh pr edit --body` で本文を上書きする場合も同様に、事前に現在の本文を取得して把握してから編集する
- ユーザーはCoding Agentsの応答を手動でコピペ・編集して先に投稿することがある。重複を検出したら投稿を中止し、ユーザーに「既に投稿済みのため重複回避でスキップした」と伝える
- 本文更新後は再取得し、依頼した内容とリンクが反映されていることを確認する

レビューコメントの返信案を書くときは、共通資料`docs/agents/output-policy.md`の「レビュー返信コメント（Reviewee）」に従い、人間向けとbot向けの文体を選ぶ。
