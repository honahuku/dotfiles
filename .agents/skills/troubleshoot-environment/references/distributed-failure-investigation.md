# 分散システムの障害原因の調査

## 原則1: 引き金（trigger）と増幅要因（amplifier）を分けて特定する

障害は多くの場合2層でできている。両方を切り分けるまで根本原因に到達したと言わない。

- **引き金**: なぜその処理が失敗・遅延したかの一次原因。例: 存在しない外部リソースへの問い合わせ、依存先の応答遅延、不正な入力
- **増幅要因**: なぜそれが表面化・可視化したかの二次条件。例: タイムアウト値、リトライ回数、リソース制限、キャッシュの有無
- 増幅要因だけ直すと「症状は隠れるが引き金が残る」状態になり再発する。逆に引き金だけ直しても、別の遅延が来れば増幅要因で再燃する
- 見分け方: 「これを直したら二度と起きないか?」と自問する。No なら増幅要因。ArgoCD 事例では GCPBackendPolicy のタイムアウト差が増幅要因、未作成 Google Group が引き金だった

## 原則2: 環境差は最短の切り分け線

「dev は通るが stg/prod は落ちる」のような環境差・個体差があるとき、差分そのものが原因の在り処を指す。

- 同じコードベース・同じ手順で挙動が違う → 環境ごとに違う設定・データ・リソースを列挙して diff を取る
- ただし環境差は**増幅要因であることが多い**。環境差を見つけても「なぜ片方だけ症状が出るか」の説明にはなるが、「そもそも何が失敗したか」（引き金）は別に残っている場合がある。原則1とセットで見る

## 原則3: レイヤーを外側から順にログで裏取りする

リクエストが通る経路（LB / Gateway → アプリ → 依存サービス）を外側から1層ずつ見る。どの層で応答が止まったかを特定してから内側の原因に入る。

- **エッジ層のログ（LB / Gateway / proxy）が最も雄弁**。status code と latency が出る。latency がタイムアウト設定値ちょうどに張り付いていたら「バックエンドが時間内に応答できなかった」サインで、原因はさらに内側
- アプリ層のログに「成功」が出ていても、エッジ層が先に諦めてエラーを返していることがある（アプリは完走、ユーザーには失敗と見える）。両方を突き合わせる
- ユーザーに見えるエラー文言（例: `upstream request timeout`）は多くがエッジ層由来。その文言を出す主体を先に特定する

## 原則4: 「手順が足りない」の前に「投入したものが実在するか」を疑う

設定・マニフェストに新しい参照（グループ名・シークレット名・エンドポイント・namespace 等）を足したあとの障害では、「追加の手順を踏み忘れた」より先に「参照先の実体が本当に存在するか」を確認する。

- 設定に名前を書くだけでは実体は生えない。外部で作るべきもの（Google Group・DNS・証明書・IAM・外部 API のリソース）の作成漏れは頻出
- オンボーディング・新規追加系のトラブルはこのパターンの確率が高い

## 調査の型（手順）

1. ユーザーに見えるエラー文言から、それを出している層を特定する
2. エッジ層のログで status/latency を見て、どの層で止まったか切り分ける（原則3）
3. 環境差・個体差があれば設定を diff する（原則2）。ただし増幅要因の可能性を頭に置く
4. 止まった処理が何を待っていたか（外部依存・参照先）を洗い、実在するか確認する（原則4）
5. 引き金と増幅要因の両方を言語化できたら根本原因（原則1）
