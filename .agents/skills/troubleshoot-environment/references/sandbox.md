# サンドボックス内の失敗からの復旧

## サンドボックス内の失敗から復旧する

サンドボックス内でaquaが最終使用日時を更新できず、`update the last used datetime`や`create a package timestamp file`とともに`read-only file system`を出すことは既知の事象として扱う。対象ツールの版・引数・実行したコード・終了状態・結果を確認し、依頼された処理が想定どおり完了していれば、この警告は無視してユーザーへ通知しない。警告を消すためだけの昇格や書き込み権限の追加も行わない。標準エラー全体を隠して他のエラーを見落とさない。

この警告はサンドボックスの書き込み制限を示す手がかりになるが、単独で実行環境を断定する根拠にはしない。対象コマンド・実行したコード・結果が当初の想定と異なる場合や、依頼を満たせたか確認できない場合は、以下の手順で許可された同じ操作をサンドボックス外で再試行する。この例外はaquaのダウンロード失敗や対象ツールの実行失敗へ広げず、既存のサンドボックス外実行が必須の操作や禁止操作の条件も変更しない。

1. 失敗したコマンド、cwd、終了コード、エラーを確認する。セッションの権限説明やツールの応答から、実際に適用されている権限も確認する。画面上のフルアクセス設定だけで、サンドボックス外で実行したと判断しない。

   通信失敗、認証エラー、404、`Permission denied`、`read-only file system`、Aquaのキャッシュ更新失敗は、サンドボックス内の結果だけで原因を断定しない。

2. 再試行する操作が、元の依頼で許可されているか確認する。書き込みは、その書き込み自体が許可されている場合だけ再試行する。前の試行で変更が一部完了していないか、読み取りで確認して重複実行を避ける。

   禁止操作は再試行しない。TruffleHogがエラーを出した場合は、AGENTS.mdの停止・報告手順を優先する。

3. サンドボックスが原因の可能性があれば、許可された同じ操作をサンドボックス外で再試行する。利用可能なツールが提供する昇格機能を使い、対象と再試行の理由を指定する。入力形式は実行環境のツール定義で確認する。通常の実行を繰り返しただけで、昇格したと扱わない。

4. 再試行が成功したら、元の依頼の未完了手順へ戻る。診断コマンドが通っただけで完了にしない。依頼された取得・検証・更新と、その確認まで進める。

5. サンドボックス外でも失敗したら、エラーに沿って認証、PATH、対象のアクセス権などを調べる。昇格できない、承認を拒否された、ログインなどの本人操作が必要な場合は、サンドボックス内外で試した結果と必要な対応を示して問い合わせる。

   委譲先は同じ情報を呼び出し元へ返す。呼び出し元は上記の手動依頼手順に従い、通常の応答本文で必要な操作を示してターンを終了する。
