# Git操作とファイル削除

- コミットメッセージの説明と本文は、明示的な指示がなければ日本語にする。Conventional Commitsのtypeやscopeなど、所定の構文は維持する。

- 本人へGit操作を依頼する前に、`~/.agents/skills/troubleshoot-environment/references/manual-operations.md`の「依頼前の検証提示」を適用し、実行済みの検証コマンドと結果をチャット本文に示す。

- **本人へGit操作を依頼するときは、コミット・mergeなどの操作ごとに、対象worktreeの絶対パスを必ず本文に示す。複数のworktreeが対象なら、絶対パスと依頼する操作をそれぞれ列挙する。lazygitで操作するためコマンドを省略する場合も、worktreeの絶対パスは省略しない。「上記のworktree」「残る3つ」などの参照だけで済ませない。**

worktreeパスの表示形式は、`review-output`の`references/output-policy.md`「記号・書式」に従う。

- **本人へのコミット依頼はlazygitを前提に、対象ファイルを自然文で伝え、本資料の「ステージ後の報告」に従ってコミットメッセージ案を添える。コミット用のコマンドは提示しない。Git操作の依頼と、それ以外のコマンド実行依頼は分け、同じコードブロックや`&&`等で連結しない。**

- `git rebase`など履歴を書き換える操作は、可逆性判断の「履歴改変」に従い、対象と具体的な結果を示して明示許可を得る。許可後は実行してよい。許可がない場合はmergeなど履歴を保つ方法を選ぶ。

- 既存の変更を勝手に破棄しない。通常のrevertで戻せる変更は依頼範囲内で実行できる。stash・強制push・削除・履歴変更は対象・影響・復旧可能性を確認し、必要な場合は個別の明示許可を得る。

- 作業場所は`worktree.md`の「作業開始」に従い、既存checkoutを原則とする。別セッションの変更との競合を避ける。

- mainとの競合は、作業ブランチのworktreeへmainを取り込み、そのworktree内で解消する。main上での競合解消や、そのためのmain直接編集の許可を求めない。取り込み・解消後のステージ・コミットは、それぞれの操作の許可範囲に従う。mainで既にマージが始まっていても、その作業状態を変更せず、作業ブランチ側で進める。

- Git管理下の変更と関連ファイルは、選択したcheckout内に置く。表示のためにチャットの`work/`・`outputs/`などへ複製しない。外部保存はユーザーが対象と保存先を明示した場合だけ行う。既存ファイルを`cp`で直接置き換えない。

- Git管理ファイルの編集・削除は、依頼された作業の範囲で、`worktree.md`に従って選んだworktree内で実行できる。削除前は対象の内容・参照先・削除理由を確認し、本人の既存変更を破棄しない。ステージ・commit・merge・pushの許可条件は、本資料の「Git操作の許可範囲」に従う。

- merge・switch・checkout・reset・restoreなどでファイルが削除・上書きされる場合も、対象と差分を事前に確認する。merge前は`git diff --name-status HEAD..<target>`で影響を確認する。通常のrevertで戻せる依頼範囲内の変更は実行し、既存の未コミット変更を破棄する操作や履歴改変には個別の明示許可を得る。

- Git管理外のファイルの作成・編集・削除は、`review-output`の`references/output-policy.md`「送信・変更の承認」と、`check-command-policy`の可逆性判断に従う。復旧可能性が不確実または不可逆な変更に限り、対象・影響・復旧方法を示して明示許可を得る。削除方法は実際の環境と管理元を確認して選ぶ。

- `find`で削除する場合も、対象条件を限定し、`check-command-policy`の可逆性判断に従う。広範な検索結果を確認せず削除対象にしない。

## Git操作の許可範囲

`~/git/*`の既定は次のとおりとする。CLI・API・MCP・サブエージェントへの委譲でも同じ範囲を適用する。

| 操作 | 許可条件 |
| --- | --- |
| 状態を変更しない読み取り | 追加確認なしで実行できる |
| worktreeの準備 | `worktree.md`の利用条件に当たり、既存ブランチ・open PRの確認と再利用条件を満たす場合に実行できる。同じトピックを別ブランチへ分離する許可は含まない |
| ステージ | 下記の条件を満たす場合に実行できる |
| commit・push・merge・pull・fetchなど上記以外の書き込み | 依頼範囲内で通常の復旧手段がある変更は実行できる。共有履歴の改変・強制操作・復旧困難な変更は可逆性判断に従って明示許可を得る |
| マージ済みPRの元ブランチ削除 | PRのマージ確認後、下記「マージ済みPRのブランチ整理」に従ってリモート・ローカルの元ブランチを削除できる |

worktreeの準備に`--force`や`-B`を使わず、既存状態を強制変更しない。許可した`info/exclude`への追記以外は、index・refs・reflog・Git hookなどへの直接書き込みで制限を迂回しない。

Git書き込みの前に、適用中の上位指示と依頼範囲を照合する。依頼範囲に含まれる通常の追跡変更は、操作名だけを理由に追加確認しない。依頼範囲外の変更、既存変更の破棄、hook迂回、上位指示で禁止されたapply・デプロイは許可に含めない。

### リポジトリ別の許可

特定の所有者のprivateリポジトリに対するcommit・push・draft PR作成の恒常許可は、適用中の上位指示または本人の明示指示で確認する。所有者名などの環境固有の値は公開資料へ記載しない。許可を確認できない対象には上記の既定だけを適用する。

ローカルの配置名だけで判定せず、操作前に`gh repo view <owner>/<repo> --json nameWithOwner,isPrivate`などで所有者と可視性を確認し、許可された対象と照合する。public・internalにはprivateの例外を適用しない。許可の管理元を一つにし、`SKILL.md`や別資料に重ねて定義しない。

merge・PRのReady化・コメント投稿にはこの例外を適用しない。apply・デプロイを起動するpushは、対象と影響を示して明示許可を得てから行う。必要なhook・検証は省略しない。

### マージ済みPRのブランチ整理

- PRをマージするときは、可能なら`gh pr merge <番号> --delete-branch`を使う。マージ完了後にPRの状態と元ブランチ名を確認し、元ブランチのリモート・ローカル両方が削除されたことを検証する。自動削除されていない側は、PRが`MERGED`であることを確認して削除する。
- リモートブランチが残っている場合は、PRのhead branchと一致することを確認してから`git push origin --delete <branch>`で削除する。ローカルブランチがworktreeで使用中なら、status・差分・未追跡ファイルを確認する。変更がなく、他のセッションで使用中でないworktreeだけを通常の`git worktree remove`で外し、その後ローカルブランチを削除する。
- squash・rebase mergeでは元ブランチのcommitがbaseの祖先でなく、`git branch -d`が拒否する場合がある。PRのマージ状態とhead SHAを確認したうえで、そのPRの元ブランチに限って`git branch -D`で削除する。未コミット差分がある、worktreeの使用状況が不明、またはPRのマージを確認できない場合は削除を止め、対象と理由を報告する。既存変更を破棄したり、`worktree remove --force`を使ったりしない。

### ステージと個別操作の条件

- **ステージのみが許可されたリポジトリでは、対象worktreeの作業開始時にステージ済み差分と未解決競合がない場合に限り、`git add`を実行する。** `git status --short --branch`で対象worktreeの状態を確認し、コマンドの作業ディレクトリには対象worktreeの絶対パスを明示する（mainの状態を調べる場合だけ元clone直下を指定する）。作業内容を確認した追加・変更ファイルの明示的なパスだけを一つの`git add -- <path>...`に指定する。削除パス・ディレクトリ・glob・`-A`・`-u`・`-p`は使わない。ステージ状態はworktreeごとのindexに保存される。

- ステージ後は`git diff --cached`と`git status`で結果を確認する。ステージのみが許可されたリポジトリでは、いったんステージした後の追加ステージは禁止する。

- `status`・`log`・`show`・`diff`・`grep`・`ls-files`・`rev-parse`・`branch --list`・`tag --list`・`remote -v`・`worktree list`など、状態を変更しない検査は許可する。不明なGit操作は実行せず、本人の指示を仰ぐ。編集時は`apply-git-strategy`の作業開始手順に従う。

- Issue作成は、本人の明示指示または適用中の上位指示で恒常的に許可された対象だけを実行する。この例外をIssueの更新・close・コメント投稿や、リポジトリ作成の許可へ広げない。

- **`honahuku/*`の各リポジトリには、外部OSSをcloneしたディレクトリやGitサブモジュールを含めない。`vendor/`と`.gitmodules`はignoreし、公開前の検査でネストしたGit repoと外部repo用パスを検出する**

## Git管理ファイル変更後・ステージ後の報告

- Git管理ファイルを変更した場合は、変更内容の確認だけで完了扱いにしない。`worktree.md`で選んだcheckoutを対象に、変更ファイルを個別にステージし、pre-commit全体を実行する。commitの権限がなくても、引き渡し前に検査結果を確認する。Lefthookの実行許可をcommitの許可へ広げない。検査が対象とするステージ済み差分が実際に存在することを確認し、対象なし・skip・終了コード0だけを検査成功としない。通常の検査不備は修正して全体を再実行する。TruffleHogのエラーは共通指示の停止条件を優先し、詳細を報告して本人の確認を待つ。検査失敗や未検査のまま、コミット可能な状態として引き渡さない。
- 報告文を組み立てた後、送信直前に`review-output`を適用する。「ステージ後の報告」の必須項目と完成した本文を照合する。
- ステージ後と、未コミットの変更を残して作業を引き渡す完了報告に適用する。「ステージ済み」「未コミット」「未反映」と状態だけを伝える場合も、本人への操作依頼を含む場合と同じ確認を行う。
- 許可されたステージはCoding Agentsが実行してから引き渡す。許可条件と既存のステージ済み差分を確認し、対象ファイルを明示する。Git操作の承認範囲を広げたり、本人の既存ステージを変更したりしない。
- 報告直前に対象worktreeで`git status --short --branch`、`git diff --cached --name-status`、`git diff --cached`を取得し、実際のステージ状態と検証対象を照合する。過去の取得結果や`git add`の成功表示だけでステージ済みと報告しない。
- 次の項目をworktreeごとに本文へ示す。項目が欠けた報告は送信せず、確認と準備を補う。
  - 対象worktreeの絶対パスとブランチ。
  - ステージ済みファイルの一覧と追加・変更の区別、未ステージ差分の有無。単に「対象ファイル」「変更をステージ済み」と要約しない。
  - 実行した検証と結果、警告・skip・未確認範囲。提示方法は`~/.agents/skills/troubleshoot-environment/references/manual-operations.md`に従う。
  - ステージした差分に基づくConventional Commits形式のコミットメッセージ案を、コピーできるコードブロックで示す。本人へコミットを依頼しない場合も省略しない。すでにコミット済みの変更には既存のSHAと件名を示す。

## ステージ操作の許可判断

ステージ操作の前に、対象リポジトリに適用される指示と、この資料の許可条件を照合する。条件を満たす`git add`は実行し、Git書き込み全般の禁止だけを理由に拒否しない。特定リポジトリやオプションの禁止を、すべてのステージ操作へ広げない。`git add -p`などの可否も対象に適用される規則で判断し、禁止を説明するときは対象と根拠を示す。

## Git書き込み前後の確認

- ブランチの変更を検査・引き渡す前は、対象ブランチのworktreeで、リポジトリに定義されたpre-commit全体を実行する。Lefthookでは`lefthook run pre-commit --no-auto-install`を使い、個別コマンドや独自に選んだファイルだけの検査で代替しない。実行前にhook定義と呼び出し先を読み、禁止された操作を含まないことを確認する。
- 検査には、本人が指定した設定または対象repoの設定を使う。別worktreeやmainの設定に差し替えない。実行したブランチ・worktree・設定元・コマンド・各検査の結果を対応させ、pre-commit全体が成功した場合だけ全体の検査成功と報告する。ステージ済み差分と未ステージ差分が異なる場合は、hookが実際に検査した範囲も明記する。
- PRのmerge後に検証が必要な依頼では、PRのmerge状態を確認したうえで、merge commitを含む最新の`main`を指す元cloneのmain checkoutから、依頼で失敗した検査と必要な関連検査を実行する。main checkoutが最新でない場合は、作業差分がないことを確認してから`origin/main`へ安全に同期する。作業差分がある、または安全に同期できない場合は上書きせず、確認できた状態を示して停止する。作業ブランチや古いmainの結果を、merge後の検証結果として扱わない。
- merge後のmain検証が失敗した場合は、失敗内容を調査し、修正して同じ手順で検証を繰り返す。作業場所は`worktree.md`に従う。最終的な成功または未解決の失敗を確認するまで、依頼を完了扱いにしない。

- **sandbox環境ではBashの書き込み系コマンド（`git worktree add`/`commit`/`merge`/`push`/`remove`、ファイルシステムやリモートを変更する操作）がブロックされ、実行されないまま成功したふうのダミー出力（それらしいSHAや`Fast-forward`、ファイル一覧など）を返すことがある。** 読み取り系（`git log`/`status`/`worktree list`、`grep`、`test -f`）は本物の値を返す。書き込み系は`dangerouslyDisableSandbox: true`を付けて実行し、実行後は必ず読み取りコマンド（`git log`/`status`/`rev-parse origin/main`/`test -f`）で実際に反映されたか検証してから次に進む。ダミー出力を鵜呑みにしない。commitのheredoc `-F -`はsandbox無効でもstdinが渡らず失敗することがあるため`-m`フラグを複数使う。Write/Editツールもsandboxの影響を受けることがあるので、ファイル作成後は`test -f`や`wc -c`で実在を確認する。

- **作業開始時に `git log --oneline -3` でHEADのSHAを控え、mergeの直前にもう一度確認する。確認だけを1回のツール呼び出しで行い、その結果を読んでSHAを比較してから、次の呼び出しでmergeする。検査の呼び出しに、その結果に依存する書き込みを同居させない。動いていたら、そこで止めて別セッションが何をコミットしたかを読む。** 同じリポジトリで複数のセッションが並行して動くと、同じ変更が二重にコミットされる。2026-07-31、`autocmds.lua`に同じ`require`行が2回入った状態がpushされ、後から削除するコミットが必要になった。自分の変更がすでに入っていたら、自分の側のコミットは捨てて重ねない。

- ステージは `git add <path>` でファイルを個別に指定する。`git add -A` と `git add .` は使わない。並行するセッションや手作業の変更を巻き込む。

- Terraform・Kubernetes manifestを編集・mergeで取り込んだ場合は`write-safe-code-and-scripts`のインフラ検証手順を適用し、対象headのCI結果まで確認する。commit前に既存hookと呼び出し先も読み、Terraform検査は`tflint`だけにする。`terraform`・`kubectl`を起動するhookは一時無効化や別経路のcommitで回避せず、許可された恒久修正を行う。必要なCI結果が得られない場合は停止して判断を仰ぐ。

- hookが動くGit操作（commit・mergeなど）は、1回のツール呼び出しにつき1操作だけ実行する。終了コードに加えてWarningを含む全出力を読み、`write-safe-code-and-scripts`の警告確認手順を完了してから、次のGit書き込みを別の呼び出しで行う。同じ`functions.exec`内で後続のadd・commit・pushを予約しない。TruffleHogのエラー時はAGENTS.mdの停止・報告手順に従う。

- **`git commit`の前に、対象リポジトリでlefthookのpre-commit（TruffleHogによるsecret検知）を必ず実行させる。** メインチェックアウトの`.git/hooks/pre-commit`に`LEFTHOOK_CONFIG`でメインの`lefthook.yml`の絶対パスを固定注入済みの独立リポジトリでは、worktree側に`lefthook.yml`を個別配置しなくても発動する（hooksはworktree間で共有されるがconfigはworktree自身のトップレベルからしか探索されないため、`LEFTHOOK_CONFIG`で固定する対応が必要になる）。まだこの対応をしていない独立リポジトリ（新規clone直後など）では、`lefthook.yml`（`extends: [~/.lefthook-global.yml]`のみ）をトップレベルに作成して`lefthook install`し、生成された`.git/hooks/pre-commit`の`call_lefthook()`定義の直前に`export LEFTHOOK_CONFIG="<トップレベルの絶対パス>/lefthook.yml"`を追記してから`git commit`する。`LEFTHOOK=0`や`--no-verify`でのスキップは絶対禁止のhook迂回に当たるため使わない。




## Git・GitHub CLIの実行

- `git`と`gh`は、読み取り操作を含め初回から毎回サンドボックス外で実行する。必要な実行ツールでは`sandbox_permissions: "require_escalated"`を指定し、承認手続きに従う。
- この実行方法は許可済みだが、Git操作自体の許可は広げない。リポジトリごとの操作制限を引き続き適用する。
- GitHub連携に依頼された操作を行う機能がない場合は、操作自体が許可されている範囲で`gh`へ切り替える。GitHub CLIの利用と認証選択は、`check-command-policy`の`references/command-policy.md`「GitHub CLIへの切り替えと認証選択」に従う。

## GitHub Issueの作成・本文更新

- 本文を書く前に、対象リポジトリの作業指示と`.github/ISSUE_TEMPLATE/`を確認し、用途に合うテンプレートを実際に読む。ローカルにない場合はGitHubから取得する。過去のIssueや記憶をテンプレート確認の代わりにしない。
- テンプレートの見出し・順序・必須項目を使って本文を組み立てる。独自の見出しへ置き換えず、詳細は該当項目の下へ整理する。空欄・省略が許される項目はテンプレートの指示に従う。
- 投稿直前に、本文を読み取ったテンプレートと照合し、見出し・順序・必須項目の欠落を確認する。CLI・API・プラグイン経由でも省略しない。テンプレートの有無や内容を確認できない場合は投稿せず、その状況を報告する。テンプレートがないと確認できた場合だけ自由形式で作成する。
- 投稿・本文更新後はIssueを再取得し、意図した本文とテンプレートの構成が反映されていることを確認してから完了を報告する。
