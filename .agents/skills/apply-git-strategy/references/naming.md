# スキル・ブランチ・コミット・タスクの命名

## 命名

- 自主管理のスキル名は英語の動詞から始め、同じ動作には同じ動詞を使う。準備は`prepare`、実作業は`execute`、文章作成は`write`、デッキ生成は`build`、評価は`review`、状態・配置確認は`check`を使い、動作が異なる場合は無理に揃えない。外部取得・外部派生のスキルは改名しない。
- 既存名の例外として`done`・`todo`・`input-kousuu`を維持する。`register`・`review`には対象を表す接尾辞を付けない。旧名の互換リンクは新しいスキル名の候補にしない。

- ブランチ名は、IDがあれば `<ID>-<type>-<topic>`、なければ `<type>-<topic>` とする。**`/` は使わない。** `/` を含むブランチ名はworktreeのパスにそのままネストされ、`TASK-123` のような親ディレクトリを複数のブランチが共有する意図しない構造を生む。
- `type` はConventional Commitsの種別を使う。
- コミットは `<type>: <日本語説明>` とし、IDを入れない。本文はdiffから分からない理由があるときだけ書く。
- **t-wadaの発言「コードには How テストコードには What コミットログには Why コードコメントには Why not を書こう」を意識して、コミット前にメッセージがWhyを伝えているか必ず確認する。** 変更一覧だけで終えず、解決する問題・変更の必要性・選択の根拠を書く。件名で理由が伝われば本文は不要。diffにあるHow・Whatの説明や作業経緯の羅列で埋めず、確認できていない理由を作らない。
- タスク名は対象URLを確認してから付ける。PR関連は `<概要> (<repo> #<number>)` とし、必要なら `(Reviewer)` または `(Reviewee)` を付ける。
- **タスクタイトルを提案する前に必ずsource_urlを開いて内容を把握する。推測で案を出さない。** レビュー関連タスクには役割接尾辞を付ける（自分がレビュアー: `PR #NNNN: ... (Reviewer)`、レビュイー: `PR #NNNN: ... (Reviewee)`）。
- **PR・タスク・Issueなど番号やIDだけで参照せず、タイトルか短い要約を必ず添える。** 例: `#123` ではなく `#123「fix: 定期処理の停止条件を修正」`。会話の中でIDを初めて出す時点で必ずタイトルか要約を先に提示する（初出でタイトルを提示済みなら、以降の同一会話内はIDだけでもよい）。AskUserQuestionの質問文・optionにIDを書くときも同じ扱いにする。
