# 技術ドキュメント・実験レポートを書く/直すときの観点

AGENTS.md コアの「出力の原則」（読み手の原則・断定と確実性・裏取り）は全出力に適用される前提。ここはドキュメント・仕様説明・実験や検証のレポートに固有の観点を扱う。対象はスタンドアローンのドキュメントに限らない。PR説明・PRコメント・Issueコメントなど、技術的な内容（設定・原因・裏取り）を含む文面全般に適用する。

## 実験・検証レポートの型

対照実験・性能比較など、何かを測って比べるレポートを書く/直すときは、この型に従う。理工系の大学・機関が公開している実験レポート指導資料から抽出したもので、ソフトウェア・インフラの対照実験にもそのまま適用できる。

- **章立ては目的→方法→結果→考察→結論の一方向構成にし、後戻りしない。** 結果を書いている途中で目的や条件を書き足さない。検証目的・比較対象と測定条件・生データ・解釈・結論の順で章を固定する
  出典: [室蘭工業大学 電気電子工学科 辻研究室「レポートの書き方」](https://u.muroran-it.ac.jp/yt-lab/Lecture/KIT/EET/report.pdf)、[名城大学理工学部応用化学科「実験レポートの書き方」](https://www1.meijo-u.ac.jp/~mozawa/education/exp/exp3/実験レポートの書き方.pdf)、[新潟大学附属図書館「実験レポートの書き方」](https://www.lib.niigata-u.ac.jp/wp-content/uploads/2023/10/experimentreport2021.pdf)、[Washington State University「Lab Report Organization」](https://labs.wsu.edu/engineering-lab-report-writing/sample-page/f2-lab-report-organization/)、[University of Toronto「The Lab Report」](https://advice.writing.utoronto.ca/types-of-writing/lab-report/)
- **結果と考察を分離する。** 結果は客観的事実として「である」「〜が見られる」調で書き、解釈は考察に「〜と考えられる」調で書く。結果の章に解釈を混ぜない。表・グラフは結果の章に置き、考察の章ではその番号を参照しながら解釈する
  出典: [名城大学](https://www1.meijo-u.ac.jp/~mozawa/education/exp/exp3/実験レポートの書き方.pdf)、[WSU](https://labs.wsu.edu/engineering-lab-report-writing/sample-page/f2-lab-report-organization/)
- **図表は形式を統一する。** 表のキャプションは表の上、図のキャプションは図の下に置く。通し番号を振り本文中では番号で参照する。軸・列・セルには単位を明記する。**番号を振ると決めたら文書内のすべての表・図に例外なく振る。** 一部の表だけに付けて残りを無題のままにしない。**キャプションの語順は「表N: タイトル」「図N: タイトル」で固定する**（表・図のラベル＋番号が先、タイトルが後）。「タイトル（表N）」のように番号を後ろに回さない
  出典: [室蘭工業大学](https://u.muroran-it.ac.jp/yt-lab/Lecture/KIT/EET/report.pdf)、[新潟大学](https://www.lib.niigata-u.ac.jp/wp-content/uploads/2023/10/experimentreport2021.pdf)、[名城大学](https://www1.meijo-u.ac.jp/~mozawa/education/exp/exp3/実験レポートの書き方.pdf)
- **考察から感想・言い訳を排除する。** 「時間がなくてできなかった」「面白かった」のような感想・言い訳・根拠のない予想は考察に書かない。運用上の制約があった場合も、制約条件と、その制約下でどこまで言えるかを事実として書く
  出典: [室蘭工業大学](https://u.muroran-it.ac.jp/yt-lab/Lecture/KIT/EET/report.pdf)、[新潟大学](https://www.lib.niigata-u.ac.jp/wp-content/uploads/2023/10/experimentreport2021.pdf)
- **誤差・限界は具体的に特定する。** 「ばらつきがあった」で済ませず、試行回数・測定間隔・ノイズ要因など具体的な要因まで踏み込む。実験設計そのものの限界も分析する
  出典: [University of Toronto](https://advice.writing.utoronto.ca/types-of-writing/lab-report/)、[WSU](https://labs.wsu.edu/engineering-lab-report-writing/sample-page/f2-lab-report-organization/)
- **今後の課題は結論に混ぜない。** 結論は新しいデータを提示せず、確定して分かることだけを短くまとめる。改善点・次回条件を変えるべき点は結論と別のセクションに分ける
  出典: [WSU](https://labs.wsu.edu/engineering-lab-report-writing/sample-page/f2-lab-report-organization/)

## 目的・課題起点の書き口

- パラメータ・設定項目を並べるとき、「これは何か」を辞書的に説明するだけで終わらせない。「`hoge` を設定するため」「`huga` の問題を解決するため」という、目的・課題を主語にした書き口にする
- 読み手はまず「自分が今困っている課題」から入って設定を探す。定義の羅列は課題からの逆引きができず、読み手が自分の状況に当てはめて考える負担を強いる

冒頭の書き出し方・列挙を終える方法など文章構造レベルの指針は review-output スキルにまとめてある。

## 設定が複数レイヤにまたがるとき

似た役割に見える設定が複数ある場合（例: Kubernetes 側のタイムアウトと Load Balancer 側のタイムアウト）、読み手は「なぜ両方必要なのか」で必ず立ち止まる。この疑問を放置しない。

- 各設定が**どのレイヤの設定か**（K8s / LB / アプリケーションなど）を明示する
- **なぜ役割分担として複数必要か**を説明する。名前や単位が似ていても、制御する対象・タイミングが違うため両方必要だと書く
- 複数の設定の関係が条件式（`A >= B + C` など）で表せる場合、その式を一次情報で確認した上で明記する。式を示さずに「うまく設定してください」で終わらせない

## 出典はインラインで示す

事実の裏取りに使ったドキュメント・実装への参照は、文末にまとめてリンク一覧を置くのではなく、**その事実を書いている箇所の近くに置く**。形式は次の2つを記述の性質で使い分け、機械的にどちらか一方へ統一しない。

### 日本語版があれば日本語版を貼る

公式ドキュメントに日本語版がある場合（例: Kubernetes 公式ドキュメントの `https://kubernetes.io/ja/docs/`）、リンク先は日本語版を優先する。ただし翻訳はページごとに状況が違う。

- 該当ページの日本語版が存在しない、または存在しても引用したい記述が古い/欠けている場合は、その記述が実際に書かれている言語のページ（通常は英語版）を貼ってよい。読み手が実際にその場で確認できることが、言語をそろえることより優先する
- 裏取りは常に一次情報の原文（多くの場合英語）で内容を確認する。日本語版はリンク先として使うだけで、翻訳文だけを読んで裏取りを済ませない。日本語版と英語版で記述に食い違いがあれば原文（英語版）を正とする
- 1つの段落内で複数ページを参照する場合、ページごとに日本語版の有無が違うことがある。段落全体で言語をそろえる必要はなく、ページ単位で判断する

- **コードブロック（式・設定例）の裏取り**: コードブロックの直後にリンク単体を1行で置く

  ```text
  preStopSleepSeconds >= drainingTimeoutSec + DRAIN_LATENCY
  ```

  [GKE でのロード バランシングのトラブルシューティング | GKE networking | Google Cloud Documentation](URL)

  リンクテキストは対象ページの title 要素をそのまま使う。WebFetch でページの title を確認してから書く（推測で作らない）。サイトによって階層数が変わる。Google Cloud は `{ページ固有のタイトル} | {プロダクト・カテゴリ名} | Google Cloud Documentation` の3階層、Kubernetes 公式ドキュメントは `{ページ固有のタイトル} | Kubernetes` の2階層など、サイトごとの構成に合わせる

- **地の文の主張の裏取り**: 主張している文そのものにインラインリンクを張る。リンクにする範囲は「その主張を述べている一節」。文末に丸括弧で URL を後置きしない。
  - ⭕ 「preStop と graceful shutdown の合計がこれを超えると [SIGKILL されます](URL)」／「preStop と graceful shutdown の合計がこれを超えると [SIGKILL されます](URL)。」のように、主張の述部ごとリンクにする
  - ❌ 「preStop と graceful shutdown の合計がこれを超えると SIGKILL されます（[Container Lifecycle Hooks | Kubernetes](URL)）」——主張の外に丸括弧で出典を付け足す形。丸括弧ゲートにも引っかかる
  - リンクにする範囲が主張の一節ですので、リンクテキストは title 要素そのままにならなくてよい（title そのままはコードブロック直後の単体リンクの場合の規則）。読み手が主張とリンク先の対応をその場で追えることを優先する
- 1つの段落に複数の主張がある場合、それぞれの裏取り元が異なるならその都度個別にリンクする。全部まとめて1つのリンクに寄せない
- 読み手は「この記述はどこで確認できるか」を、その場で追えることを優先する。まとめて出典リストを作ると、どの記述がどのリンクに対応するか読み手が探し直す必要が生じる

## 実験結果を脚注で引用する

対照実験・検証レポートの結果を要約したドキュメント（ADR・proposalなど）で、生データが別リソース（PRのdiff・Notionページなど）にある場合、脚注`[^1]`形式で参照する。文書全体で同じ生データを何度も参照するときは、番号を使い回し、URLごとにインラインリンクを繰り返さない。

- **脚注は具体的な主張・数値に付ける。** 「詳細は〇〇を参照」のような、読み手に別リソースへ移動するよう促すだけの文は書かない。事実を述べた文・具体的な数値のすぐ後に脚注番号を置く
- **「次の通り」の直後には付けない。** 「次の通り。[^1]」は`[^1]`が「次」を指しているように読める。表・図が続く場合は表・図のキャプション（後述の通し番号）に付け、箇条書きが続く場合は箇条書き中の具体的な事実に付ける
- **「次の通り」は直後に表・図が続く場合だけ使う。** 推測・考察の箇条書きを導入する文では使わない
- **表に通し番号とキャプションを付けている場合は、キャプション側に1つだけ脚注を付ける。** 表内の特定のセルにだけ付けると、なぜそのセルだけ根拠がいるのか読み手が混乱する
- **同じ数値・主張が文書内で繰り返し登場する場合、再掲のたびに脚注を付け直さない。** ただし離れたセクション（読み手がそこだけを読む可能性がある場所）であらためて数値を主張として使うときは、そのセクションでも1回は付ける

## 検証の経緯を成果物に書かない

裏を取ったこと自体（「dev環境の実time seriesで確認済み」「実際に叩いて確認した」など）は、検証行為の記録であって読み手が必要とする情報ではない。成果物（ドキュメント・PR説明・コード内コメント）には、確認して分かった**事実**だけを書く。「確認した」という経緯は削る。

- ❌ 「`backend_target_name` はルーティング解決時点の値を保持するため捕捉できます（dev環境の実time seriesで確認済み）」
- ⭕ 「`backend_target_name` はルーティング解決時点の値を保持するため捕捉できます」
- 裏取りの記録を残したいなら、行き先は成果物本文ではなくコミットログ（Why）。「〜を実データで確認した」はコミットメッセージに書く

判定条件は AGENTS.md「読み手の原則」と同じ。その一文を消しても読み手が失う情報がないなら消す。「確認済み」は消しても事実（保持される仕様）は残るので消す。

## 仕様・流れの記述ページでは含意を書かない

「◯◯のしくみ」「Aが作成されてBになるまでの流れ」のような、事実そのものを記述することが目的のページでは、事実の直後に「つまり〜」「そのため〜」と続けて、そこから導かれる含意・応用・評価を書かない。

- ❌ 「readinessProbe はコンテナの生涯を通じて実行され続ける。つまり Ready になるまでの所要時間には `periodSeconds` の設定も影響する」——前半は仕様の事実だが、後半は特定の目的（所要時間を計測したいなど）から見た応用で、この仕様ページの主題ではない
- ⭕ 「readinessProbe はコンテナの生涯を通じて実行され続ける」でやめる。応用・評価は、その目的を持つ別のページ（対照実験の設計ページなど）に書く
- 判定条件: その含意が「この事実からは一般に導ける」ものではなく、特定の目的・ユースケースを前提にした評価（できる／できない、影響する／しない、有利／不利）になっていたら、それは仕様ページの外に出す
- 目的別にページを分けている場合（仕様ページと、その仕様を使う対照実験・設計ページなど）、含意はその目的を持つページ側に書く。仕様ページから消しても、事実（仕様そのもの）は残るので情報は失われない

## ディレクトリ構成をtreeで書くとき

- **ディレクトリ構成をtree記法で書くときは、依頼者から特別な指示がない限り必ずディレクトリ優先・アルファベット順にする。** nvimなどのファイラが実際に表示する並びと一致させる
- 読む順・重要度順で見せたい場合も、tree自体の並びは変えない。tree直後の説明文や別のリストで読む順を示す
- 判定条件: tree記法（`├──`/`└──`を使う表現）を書く場面すべてに適用する。対象プロジェクトを問わない

## トグル（`<details><summary>`）の見出しの書き方

トグルを開けば説明・根拠が書かれていることは、読み手にとって自明である。見出しに「〜の根拠」「〜した理由」「〜の詳細」と明示しない。見出しには結論・ルールそのものを言い切りで書く。

- ❌ `<summary>閾値を5分間に3件超にした根拠</summary>`
- ⭕ `<summary>閾値は5分間に3件超とする</summary>`
- 判定条件: 見出しから「根拠」「理由」「詳細」を外しても、トグルの中身を読めば同じ情報が伝わるなら、その語は見出しにいらない。見出しはトグルの内容を予告する要約ではなく、トグルが答える結論を先に言い切る

## ドキュメントとコード内コメントで書き分ける

同じ事実でも、書く場所によって残すべき内容が違う（Takuto Wada 氏の「コードには How、テストコードには What、コミットログには Why、コードコメントには Why not を書こう」という整理に沿う）。

- **運用ドキュメント（docs/）**: 読み手は「なぜこの設定なのか」を知りたい。仕様・理由（why）を書く。検証の経緯や、コード実装の細部は書かない
- **コード内コメント**: How はコードが語るので書かない。書くべきは **Why not**——「なぜ一見自然に見える別の書き方をしないのか」。一見間違いに見えるコード（例: タイムアウト時に `NO_BACKEND_SELECTED` になりそうなのに `backend_target_name` で絞り込む）には、「〜だと思って余計な条件を足さないこと。理由は〜」という形で、将来の実装者が同じ迷いで手を入れるのを防ぐコメントを残す
  - 分量は質で抑える。コードから読めることを書かず、理由は1つに絞る。エラーコードなど検証時の詳細を重ねない。同じ制約を理由と失敗の様子の両方から言い直さない
- **コミットログ**: Why（なぜこの変更をしたか・何を確認して判断したか）。検証の経緯・裏取りの記録はここ

リスクを書いたら対処とセットにする、など文章構造レベルの指針は review-output スキルにまとめてある。ドキュメントでは特に起きやすいので着手前に確認する。

## レビュー対応に着手する前に

レビューコメントを受けてドキュメントを直すとき、着手前に**そのレビューのコメント全体と、コメント中の参照リンク・引用を先に全部読む**。

- レビュアーが根拠となる公式ドキュメントのリンクや、正確な条件式をコメント内にすでに貼っていることがある。それを読まずに自分の推測から書き直すと、レビュアーがすでに示した答えを無視して見当違いの説明を重ねることになる
- 複数のインラインコメントがある場合、個別に反応する前に全体を俯瞰し、同じ論点への言及がまとまっていないか確認する
