# 技術文書の構成と変更理由の説明

## 文体と簡潔さ

- 出力する文章は、原則としてだ・である調にする。明示された文体指定や引用の原文は尊重する。
- 一文は一つの内容に絞る。理由・条件・補足を重ねる場合は文を分ける。
- PRでは変更があることは自明である。「〜をする変更である」と説明せず、「〜をする」「〜をしたい」のように動作や目的を直接書く。意図と実装済みの事実は区別する。
- 各段落は一つの論点に絞る。見出しで論点を分け、並列の項目や手順には箇条書きを使う。
- 参照だけでは足りない判断材料を残す。必要な説明を一文へ詰め込んだり、重複をトグルに隠したりしない。


## 変更の理由と技術的な認識

変更や対象外の理由がレビューに必要なら、既存の説明先で足りるかを先に確かめる。未説明の根拠だけを適切な場所に補い、すべての変更についてPR本文へ理由を書き足さない。

- 理由が分からなければ、ユーザーに確認し、議論してから書く。もっともらしい理由を作らず、理解できていない判断を確定した説明にしない。
- 将来の実装者に必要な理由はコードコメントやdocsに残し、PRでは必要に応じてそこを参照する。理由を各所へ重ねて書かず、実装を言い直すコメントも追加しない。
- 確認方法を書く前に、観測する応答がどの処理・レイヤーから返り、何を確認できるかを、要件・コード・設定・ログで照合する。到達、認可、処理成功を混同しない。
- 技術的な認識の訂正は、言い回しの変更だけとして扱わない。誤っていた前提を直し、関連する説明と確認条件にも反映する。

### ファイルの差分と実際の影響を分ける

変更内容・対象外・チェックリストを書く前に、変更した設定を既存のどの設定や処理が参照するか確認する。編集していないファイルでも、参照先の変更によって権限、レビュー対象者、実行時の動きが変わる。

- チーム・ロール・参照先を変更する場合は、今回の判断に必要な参照元まで追い、変更前後で誰が何をできるようになるかを説明する。成立条件はコード・設定・公式仕様で確認し、未確認の影響は断定しない。
- 「変更なし」「対象外」は、ファイルの編集範囲と、実際の権限・挙動への影響のどちらを指すか明示する。ファイルに差分がないことだけを根拠に、影響がないと説明しない。
- 例: CODEOWNERSに指定されたチームへメンバーを追加すると、CODEOWNERSファイルを編集しなくても、Code Ownerとしてレビュー・承認するメンバーが変わる。チームの可視性と対象リポジトリへのwrite権限を確認する。Code Ownerとしての役割を、リポジトリやOrganizationの管理権限と混同しない。


## 目的・課題起点の書き口

- パラメーター・設定項目を説明するときは、何のために設定するか、どの課題を解決するかを先に書く。目的を示すために主語と述語の対応を崩さない
- 読み手はまず「自分が今困っている課題」から入って設定を探す。定義の羅列は課題からの逆引きができず、読み手が自分の状況に当てはめて考える負担を強いる

文章表現の自然さ、語彙、括弧、冗長さ、英日間の空白はyomiyasuに任せる。このスキルでは技術文書の目的、構成、対象読者、事実関係、出典を確認する。


## 検証の経緯を成果物に書かない

このセクションは、仕様の説明に検証の経緯を混ぜないための規則である。PRのTest planと実験・検証レポートには、判断に必要な確認方法・結果・未確認事項を残す。

裏を取ったこと自体（「dev環境の実time seriesで確認済み」「実際に叩いて確認した」など）は、検証行為の記録であって読み手が必要とする情報ではない。成果物（ドキュメント・PR説明・コード内コメント）には、確認して分かった**事実**だけを書く。「確認した」という経緯は削る。

- NG: 「`backend_target_name` はルーティング解決時点の値を保持するため捕捉できます（dev環境の実time seriesで確認済み）」
- 良い例: 「`backend_target_name`はルーティング解決時点の値を保持するため、対象を捕捉できる」
- 裏取りの記録を残したいなら、行き先は成果物本文ではなくコミットログ（Why）。「〜を実データで確認した」はコミットメッセージに書く

判定条件は共通資料`~/.agents/skills/review-output/references/output-policy.md`の「読み手の原則」と同じ。その一文を消しても読み手が失う情報が無いなら消す。「確認済み」は消しても事実（保持される仕様）は残るので消す。


## ドキュメントとコード内コメントで書き分ける

同じ事実でも、書く場所によって残すべき内容が違う（Takuto Wada 氏の「コードには How、テストコードには What、コミットログには Why、コードコメントには Why not を書こう」という整理に沿う）。

- **運用ドキュメント（docs/）**: 読み手は「なぜこの設定なのか」を知りたい。仕様・理由（why）を書く。検証の経緯や、コード実装の細部は書かない
- **コード内コメント**: Howはコードが語るので書かない。将来の実装者に必要な判断の理由を残す。特にWhy notとして、一見自然な代替案を採らない理由を書く。一見間違いに見えるコードには、変更すべきでない理由を短く添える
  - 分量は質で抑える。コードから読めることを書かず、理由は1つに絞る。エラーコードなど検証時の詳細を重ねない。同じ制約を理由と失敗の様子の両方から言い直さない
- **コミットログ**: Why（なぜこの変更をしたか・何を確認して判断したか）。検証の経緯・裏取りの記録はここ

リスク、制約、失敗条件を書いたら、読み手が取るべき対処も書く。

## セットアップ手順

- 手動のコマンド実行が5回以上になる場合は、既存の設定やタスクで自動化できないか検討し、文書には短い実行入口を示す。使用するツールは対象プロジェクトの方針に従う。
- 文書には前提、実行コマンド、利用者の判断が必要な例外だけを残す。設定ファイルや公式手順で分かる説明を繰り返さない。
