# 出典の示し方と仕様・解釈の区別

出力先だけで必要な情報を理解できるための共通条件は、`../../review-output/references/output-review.md`の「参照資料と出力先の自己完結性」に従う。以下では、事実・仕様の出典を示す方法と、共有範囲に応じた出典整理を扱う。

## 出典はインラインで示す

事実の裏取りに使ったドキュメント・実装への参照は、文末にまとめてリンク一覧を置くのではなく、**その事実を書いている箇所の近くに置く**。形式は次の2つを記述の性質で使い分け、機械的にどちらか一方へ統一しない。

### 日本語版があれば日本語版を貼る

公式ドキュメントに日本語版がある場合（例: Kubernetes 公式ドキュメントの `https://kubernetes.io/ja/docs/`）、リンク先は日本語版を優先する。ただし翻訳はページごとに状況が違う。

- 該当ページの日本語版が存在しない、または存在しても引用したい記述が古い/欠けている場合は、その記述が実際に書かれている言語のページ（通常は英語版）を貼ってよい。読み手が実際にその場で確認できることが、言語をそろえることより優先する
- 裏取りは常に一次情報の原文（多くの場合英語）で内容を確認する。日本語版はリンク先として使うだけで、翻訳文だけを読んで裏取りを済ませない。日本語版と英語版で記述に食い違いがあれば原文（英語版）を正とする
- 1つの段落内で複数ページを参照する場合、ページごとに日本語版の有無が違うことがある。段落全体で言語をそろえる必要はなく、ページ単位で判断する

- **コードブロック（式・設定例）の裏取り**: コードブロックの直後にリンク単体を1行で置く

  ```
  preStopSleepSeconds >= drainingTimeoutSec + DRAIN_LATENCY
  ```
  [GKE でのロード バランシングのトラブルシューティング | GKE networking | Google Cloud Documentation](URL)

  リンクテキストは対象ページのtitle要素をそのまま使う。WebFetchでページのtitleを確認してから書く。推測で作らない。サイトによって階層数が変わる。Google Cloudは `{ページ固有のタイトル} | {プロダクト・カテゴリ名} | Google Cloud Documentation` の3階層、Kubernetes公式ドキュメントは `{ページ固有のタイトル} | Kubernetes` の2階層など、サイトごとの構成に合わせる

- **地の文の主張の裏取り**: 主張している文そのものにインラインリンクを張る。リンクにする範囲は「その主張を述べている部分」。文末に括弧でURLを後置きしない。
  - 良い例: 「preStopとgraceful shutdownの合計がこれを超えると、コンテナは[SIGKILLされる](URL)。」のように、主張の述部ごとリンクにする
  - NG: 「preStop と graceful shutdown の合計がこれを超えると SIGKILL されます（[Container Lifecycle Hooks | Kubernetes](URL)）」。主張の外に括弧で出典を付け足す形。主張の述部にリンクを置く
  - リンクにする範囲が主張を述べている部分なので、リンクテキストは title 要素そのままにならなくてよい（title そのままはコードブロック直後の単体リンクの場合の規則）。読み手が主張とリンク先の対応をその場で追えることを優先する
- 1つの段落に複数の主張がある場合、それぞれの裏取り元が異なるならその都度個別にリンクする。全部まとめて1つのリンクに寄せない
- 読み手は「この記述はどこで確認できるか」を、その場で追えることを優先する。まとめて出典リストを作ると、どの記述がどのリンクに対応するか読み手が探し直す必要が生じる


## 仕様・流れの記述ページでは含意を書かない

「◯◯の仕組み」「Aが作成されてBになるまでの流れ」のような、事実そのものを記述することが目的のページでは、事実の直後に「つまり〜」「そのため〜」と続けて、そこから導かれる含意・応用・評価を書かない。

- NG: 「readinessProbeはコンテナの生涯を通じて実行され続ける。つまりReadyになるまでの所要時間には`periodSeconds`の設定も影響する」。前半は仕様の事実だが、後半は特定の目的（所要時間を計測したい等）から見た応用で、この仕様ページの主題ではない
- 良い例: 「readinessProbe はコンテナの生涯を通じて実行され続ける」で止める。応用・評価は、その目的を持つ別のページ（対照実験の設計ページ等）に書く
- 判定条件: その含意が「この事実からは一般に導ける」ものではなく、特定の目的・ユースケースを前提にした評価（できる／できない、影響する／しない、有利／不利）になっていたら、それは仕様ページの外に出す
- 目的別にページを分けている場合（仕様ページと、その仕様を使う対照実験・設計ページ等）、含意はその目的を持つページ側に書く。仕様ページから消しても、事実（仕様そのもの）は残るので情報は失われない

## 共有範囲に応じた出典の整理

共有資料を書くときは、宛先と想定読者を確認し、資料の共有範囲と各出典を読める人の範囲を合わせる。社内の全社員向け公開チャンネルも、インターネット上の公開情報とは区別する。

- DM・グループDM・個人用の非公開ページなど、想定読者が閲覧できない出典のURL、ページ名、発言者、日時、議事録への言及といった由来の手掛かりを、共有本文に残さない。
- 社内の全社員向け公開チャンネルや全社員が閲覧できる共有ページなど、想定読者が実際に閲覧できる出典への有用な参照は残してよい。自分が閲覧できることや、非公開表示がないことだけで読者も閲覧できるとは判断しない。外部向け資料には、外部の読者が閲覧できる出典だけを示す。
- 出典の由来を示さない場合も、そこから導いた課題・論点・判断条件を、説明として必要な範囲で本文に残す。単にリンクを外して「この指摘」「同資料」などの参照表現を残さない。
- 出典表示を整理する過程で、未確認の事実・提案・未合意事項を確認済み・合意済みへ変えない。根拠を示せず誤解を招く主張は、確実性を保った表現に直すか、本文から外す。
- 出典の閲覧可能性と、記載内容そのものを共有してよいかは別々に確認する。出典を隠すことは、個人情報・秘密情報・非公開の契約情報を共有する許可にならない。

## 置き換え資料の自己完結性

既存資料を置き換える場合、引き続き採用する前提、役割、期待、評価軸、進め方、判断材料は、新しい本文に取り込む。読み手が旧資料やそのリンク先を開かなくても、目的に必要な内容を理解できる状態にする。関連資料へのリンクを残す場合も、本文の説明をリンク先に依存させず、必要なら関連情報として一か所にまとめる。

評価方法を作る草案や記入式テンプレートでは、未知の担当者・数値・実施状況・合意を創作しない。未確定の値は本文末尾の一覧にまとめず、その情報を説明する項目に記入欄やTODOとして置き、値を埋めれば資料が完成する形にする。空欄そのものを実測結果の不足として扱わず、独立読者レビューでは資料の段階と意図を最小限の情報で伝える。
