# コマンド実行の規則

## 外部の承認レビューへ渡す根拠

自動レビューが、会話で読んだ資料やリンク先を参照できるとは限らない。実行要求に理由・根拠を渡せる欄がある場合は、次の情報をその欄に含める。チャットでの説明だけで代用しない。

- 本人が指定した指示の参照経路、規則の管理元の絶対パス、該当する禁止事項と許可例外の原文を示す。許可対象・起動方法・適用条件を一緒に照合し、「許可済み」という要約だけにしない。Git操作の根拠は`apply-git-strategy`の資料も確認する。
- 実際のcwd、実行ファイル・対象ファイルの絶対パス、引数、副作用を示し、どの条件を満たすか対応させる。禁止対象で例外がない操作は実行要求を出さない。根拠を渡す欄がない場合も、コマンドへのコメント追加やラッパーで代用せず、ツールが受け取る情報と未確認の範囲を報告する。
- worktree内では、登録済みworktreeと元cloneの対応、適用するスキルの実体・管理元を確認する。取得スキルは同期定義・lockfile・対象ファイルの差分を照合する。パスに`.worktree`や許可対象と同じスキル名が含まれるだけでは、許可の根拠にしない。
- 拒否された場合は理由を管理元の規則と照合する。確認済みの許可条件など、前の要求に欠けていた根拠がある場合だけ、その根拠を添えて再審査へ出す。同じ要求の反復、別ツール・別名・ラッパーによる迂回は行わない。解消できなければ`troubleshoot-environment`に従う。

## aqua管理の実行ファイル

- 原則：aqua管理ディレクトリ内のバイナリ・実行ファイルを、パス指定で直接実行しない。
- 対象範囲
    - `~/.local/share/aquaproj-aqua/bin/uv`などの起動リンク。
    - `pkgs/`配下の実体。
    - 本人に提示する手動実行用コマンド。
- 許可する起動方法
    - `uv`・`gh`など、通常のコマンド名でPATHから起動する。
- 詳細は`troubleshoot-environment`を参照する。

## Terraform・Kubernetes・デプロイ

### 実行禁止

- Coding AgentsによるTerraform applyとデプロイの実行は、全環境で例外なく絶対禁止とする。
    - 実行はユーザー本人が行う。
    - 禁止の解除や例外を選択肢として提案しない。
    - 「作成して」「デプロイしたい」という依頼を実行許可と解釈しない。
    - 別のCLI・API・コンソール操作、CI/CDの起動・承認、適用やデプロイを起動するmerge・push、サブエージェントへの委譲でも代行しない。
- Coding Agentsによる`terraform`・`kubectl`の実行は、全環境で例外なく絶対禁止とする。
    - 読み取り、fmt、validate、plan、dry-runも禁止する。
    - hook・ラッパー・別名・代替実装・サブエージェント経由でも代行しない。
- 許可する作業
    - コード編集、許可された静的検査、CI結果の取得。
- Terraform関連のcommit hookで行うTerraform検査は`tflint`だけにする。Terraform CLIを起動しない。

### 変更後の検証

- Terraform・Kubernetes manifestの変更後は、リポジトリのCI定義に沿って、利用可能な許可済みツールをローカル実行する。
- 禁止コマンドによる検査は、対象Git SHAのCI実行・完了結果・ログで確認する。
- 品質を確認できない場合
    - 必要なCIが未実行・skip・結果取得不可などの場合は停止し、判断を仰ぐ。
    - 別の方法で代替しない。
- 検査で誤りが見つかった場合
    - 単純な誤りは修正する。
    - 判断が必要なリソースの変更・削除・置換や、権限・停止影響は確認する。
- 詳細は`write-safe-code-and-scripts`のインフラ検証手順に従う。

### plan結果と実行手順

- CIのTerraform planは、対象環境・Git SHA・実行コマンド・終了状態と、保存plan・ログを対応させて確認する。
- 本人からplanの実行手順を求められた場合
    - 試行専用ディレクトリに`-out`・`-no-color`でplanを保存する。
    - 標準出力・標準エラー・終了コード・cwd・Terraformバージョンも残す手順を示す。
- 原本は編集・上書き・削除しない。再試行・マスキングは別ファイルにする。
- 秘密情報を含み得るログはGitへ登録しない。
- 意図しない削除を`-target`や`-refresh=false`で隠さない。
- Coding AgentsによるTerraform CLI・apply・デプロイの実行禁止は変わらない。

## AWS CLIの実行条件

- 原則：Coding AgentsはAWS CLIを実行しない。AWS CLI実行ファイルの起動をコマンド単位で拒否する。
    - 別名・ラッパー・別ツール・サブエージェントによる代行も禁止する。
- 許可する読み取り・検索
    - 検索語・通常の引数・ファイルパスに`aws`が含まれるだけの操作。
    - 利用可能なMCPによる読み取り調査。
- MCPの利用も、既存のapply・デプロイ・リソース変更の禁止を解除しない。
- CLIが必要な場合は、`~/.agents/skills/troubleshoot-environment/references/manual-operations.md`の「AWS CLIの手動実行」に従い、ログ保存付きのコマンドを本人へ提示する。

## 汎用プログラミング言語

### 原則

- `python`・`python3`・`node`・`ruby`・`perl`など、汎用プログラミング言語をコマンドとして実行しない。
- ワンライナーや任意のスクリプト実行も禁止する。
- `npx`・`npm exec`などによる任意パッケージの取得・実行も禁止する。許可する対象と実行方法は、下記の「許可する例外」に従う。
- ただし、`~/.codex/skills/.system/skill-creator/scripts/*.py`は明示的に実行を許可する。下記のskill-creatorの例外を優先し、追加確認を求めない。
- `rg`・`jq`・`awk`・`sed`で代替できない場合はユーザーに相談する。

### 許可する例外

これら許可はセッションをまたいで適用し、追加確認を不要とするが、任意のコード実行へ許可を広げない。

- yomiyasu
    - 対象：適用するyomiyasuスキル付属の`scripts/*.py`。特定のファイル名には限定しない。
    - 起動方法：配置先を確認し、`python3 <スクリプトの絶対パス> ...`で実行してよい。セッションを問わず追加確認を求めない。
    - 登録済みworktreeの配置も、適用するスキルの管理元・取得定義と対応し、付属スクリプトであることを確認できれば対象とする。配置場所だけを理由に例外を失効させない。
    - この例外を汎用言語の実行禁止より優先する。`python3 -c`などの任意コード、スキル外のファイルや同名ディレクトリに独自作成したスクリプトには許可を広げない。
- skill-creator
    - 対象：`~/.codex/skills/.system/skill-creator/scripts/*.py`。このディレクトリに付属するPythonスクリプトをすべて明示的に許可し、`quick_validate.py`に限定しない。
    - スキル作成・更新後の`quick_validate.py <スキルのディレクトリ>`による検証も、この例外に含む。追加の実行許可を求めない。
    - 起動方法：実行に必要な`python`・`python3`・`uv run`も許可する。
    - 実行前に上記ディレクトリに付属する既存スクリプトであることを確認し、絶対パスで指定する。別ディレクトリの同名スクリプトや独自作成したスクリプトへ許可を広げない。汎用言語の実行禁止を理由に、この検証を未許可と扱わない。
    - PyYAMLが不足する場合は、`uv run --with pyyaml python <skill-creator配置>/scripts/quick_validate.py <対象スキル>`で検証してよい。
- Renovate
    - 対象：`renovate-config-validator`と`renovate`のローカル実行。
    - 起動方法：`npx --yes --package renovate -- renovate`または`npx --yes --package renovate -- renovate-config-validator`で始まり、そのCLIへ引数を渡すコマンドに限り、パッケージの取得と実行を追加確認なしで許可する。
    - この例外を任意パッケージ・任意コードの実行禁止より優先する。他のパッケージ・実行方法へ許可を広げず、実行モードは下記の「Renovateの実行モード」に従う。
- 環境固有の既存hook
    - 許可される例外は、適用中の上位指示で確認する。

### Renovateの実行モード

- ローカル実行依頼で`--dry-run=`の指定がない場合は、次の両方を別々に、この順で必ず実行する。
    1. `--platform=local --dry-run=extract`
    2. `--platform=local --dry-run=lookup`
- モードが明示された場合は、その指定に従う。
- 各実行で指定した`--dry-run=<値>`と実際の動作モードを、毎回省略せず報告する。
- 情報不足時の追加検証は、`review`スキルの`references/renovate-review.md`に従って提案する。明示指示なしに`full`へ広げない。
- リモートへの書き込みやデプロイを起動しない。

## シェルスクリプトと実行権限

### スクリプトの実行方法

- 原則：`bash`・`sh`・`zsh`など、インタプリタ経由でのスクリプトファイル実行を全面禁止する。`bash foo.sh`などが対象となる。
- 実行が必要なスクリプトは、ユーザーに実行権限（`chmod +x`）を付与してもらい、`./foo.sh`の形でパスを直接指定して動かす。
- 明示的に実行を許可するスクリプト
    - 対象：公開dotfilesの`bin/check-skill-safety.sh`と、公開前検査の`bin/check-public-candidate.sh --worktree`・`--staged`。
    - 起動方法：`./bin/<スクリプト名>`で直接実行する。インタプリタ経由では呼び出さない。

### 実行権限の変更

- `chmod`は絶対に実行しない。実行権限の変更は必ずユーザー自身が行う。
- 実行権限が必要なら、`chmod`コマンドをそのまま提示し、ユーザーに実行してもらう。
- 共通hookの`~/.agents/hooks/command-policy.jq`で、`chmod`の起動を拒否する。

## GitHub APIとコメント投稿

### gh apiの実行条件

- 原則：`gh api`には必ず`--method GET`を明示する。書き込み（POST・PUT・PATCH・DELETE）は禁止する。
- 書き込みを許可する例外（sync-github用）は、次の2パターンだけとする。
    - 通知スレッドの既読化：`gh api --method PATCH "notifications/threads/<id>"`
    - 通知スレッドの購読解除：`gh api --method DELETE "notifications/threads/<id>/subscription"`

### PR・Issueへのコメント

- ユーザーがその場で明示的に投稿してよいと言うまで、コメントを投稿しない。
    - 新規コメント・レビュー返信を含み、手段を問わない。
    - `gh pr comment`・`gh issue comment`・`gh api --method POST`なども対象となる。
- 投稿前に文面を提示し、可否を確認する。
- 投稿許可として扱わないもの
    - 「直して」「反映して」「対応して」というコード修正・コミット・pushまでの指示。
    - 過去のセッションでの許可。
- 以前には`gh api --method POST`によるレビュー返信が、API書き込み禁止に抵触したまま実行され、ユーザーの事後指摘で発覚した。

## 計算

- 暗算・手計算で数値を出さない。ケタ間違い・丸め誤りを防ぐため、ツールを使う。
- 既存ツールが計算済みの値を返す場合
    - `tasks`などの返却値をそのまま使い、計算し直さない。
- ツールにない数値計算が必要な場合
    - 割合・合計・時間換算などは`bc -l`を使う。

## hookの実行と停止

### hookの起動方法

- hookの`command`を、`bash <path>`・`sh <path>`などインタプリタ経由で呼ばない。
- 実行権限が必要ならユーザーに付与してもらう。本人による実行権限の付与を迂回しない。
- 共通hookの`~/.agents/hooks/hook-settings-policy.jq`で、設定変更に含まれるインタプリタ経由のhook起動を拒否する。

### hookの迂回禁止

- `git -c core.hooksPath=<path>`による差し替え、`--no-verify`による無効化、環境変数による抑止など、統制をその場だけ外す操作を禁止する。
- commit-msg・pre-commitなど、すべてのhookを対象とする。
- hookが作業を妨げる場合は迂回せず、hook自体の条件を直す案をユーザーに出す。
- 共通hookの`~/.agents/hooks/command-policy.jq`で、コマンドに含まれるhook迂回指定を拒否する。

### TruffleHogエラー時

秘密情報を誤ってコミットする事故を防ぐため、次の停止・確認手順を守る。

- 回避策を試さず停止し、なぜエラーが出ているのかユーザーに必ず確認する。
- 報告前に確認する情報
    - 終了コード、検出件数、Detector Type、Raw result、Decoder Type。
    - ファイル、行番号、検出対象が今回の変更か既存内容か。
- 出力の詳細とともに報告する。
- 検出対象が今回の変更範囲外に見えても、確認前に先へ進まない。
    - hook設定の変更、別のコミット方法、差分の分割、履歴の作り替えなどで回避しない。
- 確認前に実行してよいこと
    - TruffleHogの出力を隠さず読むこと。
    - 検出内容を報告するための確認。

## Kubernetes contextの本人操作

- contextの切り替えが必要なら、本人に`kubectx`を案内する。
- 使用後は`kubectx -u`でcontextを未設定化する。
- Coding Agentsが`kubectl`や、それを起動するラッパーでcontextを操作しない。

## コマンドと出力

### 単一コマンド

- 各`exec_command`の`cmd`は単一コマンドにする。
- 実行直前に、コマンドを連結するシェル演算子がないか確認する。
- 禁止する連結
    - `&&`・`;`・`|`などによる複数コマンドの連結。
    - 読み取り結果を`head`・`grep`へ渡すパイプ。
- 独立した処理は個別のツール呼び出しにする。`functions.exec`内では、複数の`exec_command`をPromise単位で並行化する。
- 絞り込みは元コマンドのオプションか、`functions.exec`が受け取った結果に対して行う。

### 出力とログ

- エラー出力を理由なく隠さない。
- 標準出力・標準エラーをログへ保存する場合も、実行中にターミナルへ同時表示する。
- TTYを必要とする場合
    - 子プロセスの標準入出力がTTYとして見える記録方法を使う。
    - 例：util-linuxの`script -qefc '<command>' <session.log>`。
    - `tee`へのリダイレクトで子プロセスのTTY判定を失わせない。
- ログだけへ流し、実行中に画面で確認できない手順は提示しない。

## 個別ツールの実行条件

### tasksの実行条件

- 実行環境で解決できる`tasks`を使う。PATH上の実行ファイルだけでなく、既存のalias・関数も対象とし、実体パスを固定しない。
- ユーザーと同じalias・関数を利用できることを前提とする。使えない場合は環境の不具合として扱い、`troubleshoot-environment`に従って、まず`.bashrc`などの読み込み経路・条件を確認する。不備があれば修正する。
- 初期化を確認・修正しても見つからない場合に、同じ実行シェルで`type tasks`を確認する。`which`の出力だけで存在しないと判断せず、実体パスも推測しない。
- 読み取りでもロックファイルを作るため、必ずサンドボックス外で実行する。
- 毎回`sandbox_permissions: "require_escalated"`を指定する。
- サンドボックス内で試してから再実行する手順にしない。
- ユーザーへの追加確認は不要とする。

### 環境固有の実行許可

- バックアップの実行条件・許可される副作用は、本人の明示指示または適用中の上位指示で確認する。汎用手順を新たな操作許可として扱わない。

### prhの実行条件

- `.agents/prh/*.yml`をルールとして使うprh検査に必要な`npx`の実行を、本人の明示許可として扱う。prhパッケージの取得と起動も許可範囲に含め、追加確認を求めない。`~/.agents/prh/`への配置後も同じ許可を適用する。任意のパッケージやJavaScriptの実行には広げない。
- 実行を許可する条件
    - `write-technical-docs`が技術文書の表記規約を明示的に検査するときだけ。
    - スキル・共通資料に記載した技術手順の検査も対象とする。
- 実行コマンド：`npx --yes --package prh -- prh --rules ~/.agents/prh/rules-technical-ja.yml <file>`
- 必ずサンドボックス外で実行する。
