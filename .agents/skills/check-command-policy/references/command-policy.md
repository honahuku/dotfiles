# コマンド実行の規則

## 可逆性に基づく操作判断

操作の許可は、コマンド名や「破壊的」という分類だけで一律に決めず、対象・影響範囲・復旧可能性・本人の許可を確認する。禁止や確認要求の判断はここに集約し、各ツールの説明では固有の制約だけを記す。

1. **読み取り・一時的で容易に戻せる変更**は、依頼の範囲内で実行する。既存の`type`、alias、管理ツール、履歴などを調べ、`rm`がtrash関数へ解決される場合のような環境差も確認する。復旧できると決めつけず、実際の挙動を確認する。
2. **Gitで追跡され、通常のrevertや修正コミットで戻せる変更**は、対象と差分が依頼範囲内で、既存の未コミット変更を壊さないことを確認して実行する。通常のコミットを履歴へ追加する操作は、依頼内容とリポジトリ固有のGit許可に従う。
3. **復旧手段がない、復旧が不確実、共有履歴・本番状態・外部データに影響する操作**は、事前に対象・具体的な変更・影響範囲・復旧手段または復旧不能性を示し、その操作への明示許可を得る。明示許可後は、その範囲内で実行し、事後確認する。許可を得た後に同じ許可を再度求めない。
4. **履歴改変や既存状態の強制破棄**（例: `reset --hard`、強制push、履歴の書き換え、ユーザー変更の破棄）は、復旧可能に見えても通常のrevertとは異なるため、対象と具体的な方法を示した個別の明示許可が必要。許可された操作は実行してよい。
5. 依頼の目的・対象が特定できない、影響が説明できない、または許可が必要な事項の許可がない場合に限り停止して確認する。禁止された別経路へ迂回せず、許可済みの確認・準備は先に行う。

上位指示や法律・安全要件が特定の操作を明示的に禁止する場合、この判断軸で解除しない。操作上の承認は、対象・目的・範囲を限定して解釈する。

## 外部の承認レビューへ渡す根拠

自動レビューが、会話で読んだ資料やリンク先を参照できるとは限らない。実行要求に理由・根拠を渡せる欄がある場合は、次の情報をその欄に含める。チャットでの説明だけで代用しない。

- 本人が指定した指示の参照経路、規則の管理元の絶対パス、該当する禁止事項と許可例外の原文を示す。許可対象・起動方法・適用条件を一緒に照合し、「許可済み」という要約だけにしない。Git操作の根拠は`apply-git-strategy`の資料も確認する。
- 実際のcwd、実行ファイル・対象ファイルの絶対パス、引数、副作用を示し、どの条件を満たすか対応させる。禁止対象で例外がない操作は実行要求を出さない。根拠を渡す欄がない場合も、コマンドへのコメント追加やラッパーで代用せず、ツールが受け取る情報と未確認の範囲を報告する。
- worktree内では、登録済みworktreeと元cloneの対応、適用するスキルの実体・管理元を確認する。取得スキルは同期定義・lockfile・対象ファイルの差分を照合する。パスに`.worktree`や許可対象と同じスキル名が含まれるだけでは、許可の根拠にしない。
- 拒否された場合は理由を管理元の規則と照合する。確認済みの許可条件など、前の要求に欠けていた根拠がある場合だけ、その根拠を添えて再審査へ出す。同じ要求の反復、別ツール・別名・ラッパーによる迂回は行わない。解消できなければ`troubleshoot-environment`に従う。

## サンドボックス外での再実行

- サンドボックスの読み取り専用領域などが原因で、通常は許可されているコマンドが失敗した場合は、失敗理由と対象コマンドを示して本人にサンドボックス外での再実行許可を求める。サンドボックス外の実行が必要なのに、失敗報告だけで作業を止めない。
- この環境ではGit、Lefthook、TruffleHogのサンドボックス外実行を本人が明示許可している。これらを使う作業は個別に許可を求めず、失敗したコマンドを`require_escalated`で再実行する。許可はGit操作の種類や範囲を広げない。
- その他のコマンドは、本人が明示許可した後に限り、承認レビューへ対象・引数・副作用と根拠を示してサンドボックス外で実行する。許可されたコマンドを別の操作へ広げず、同じコマンドを再実行する。

## findによる削除

- 削除条件・対象が限定され、復旧可能性を確認できる場合は「可逆性に基づく操作判断」を適用する。広範な探索結果を未確認のまま削除対象にしない。明示許可が必要な削除は、対象を示して許可を得てから実行する。

## aqua管理の実行ファイル

- 原則：aqua管理ディレクトリ内のバイナリ・実行ファイルを、パス指定で直接実行しない。
- 対象範囲
    - `~/.local/share/aquaproj-aqua/bin/uv`などの起動リンク。
    - `pkgs/`配下の実体。
    - 本人に提示する手動実行用コマンド。
- 許可する起動方法
    - `uv`・`gh`など、通常のコマンド名でPATHから起動する。
- 詳細は`troubleshoot-environment`を参照する。

## Terraform・Kubernetes・デプロイ

### 実行条件

- `terraform`・`kubectl`の読み取り・検証・planは実行できる。結果を確認し、警告を隠さない。
- リソースや本番状態を変更する操作（`apply`・`destroy`・`import`・`kubectl apply/delete/patch/edit/scale`など）とデプロイは、可逆性判断の「復旧手段がない、または不確実な操作」に当たる。対象環境・対象リソース・差分・影響・復旧方法または復旧不能性を示し、その操作への明示許可を得てから実行する。許可後は、同じ対象・範囲で再確認を重ねない。
- 許可のない状態変更は行わない。依頼に「作成して」「デプロイしたい」とだけ書かれている場合は、対象・影響を具体化して許可を得る。
- Terraform関連のcommit hookで行う検査は`tflint`とし、Terraform CLIを起動しない。

### 変更後の検証

- Terraform・Kubernetes manifestの変更後は、リポジトリのCI定義に沿って、利用可能なツールをローカル実行する。CLIが使えない場合は、対象Git SHAのCI実行・完了結果・ログで確認する。
- 品質を確認できない場合
    - 必要なCIが未実行・skip・結果取得不可などの場合は、不足する結果と状態を示して判断を仰ぐ。
- 検査で誤りが見つかった場合
    - 単純な誤りは修正する。
    - リソースの作成・変更・削除・置換や、権限・停止影響は、対象・影響・復旧方法を示して確認する。
- 詳細は`write-safe-code-and-scripts`のインフラ検証手順に従う。

### plan結果と実行手順

- planは、対象環境・Git SHA・実行コマンド・終了状態と、保存plan・ログを対応させて確認する。
- 実行手順を示す場合は、試行専用ディレクトリに`-out`・`-no-color`でplanを保存し、標準出力・標準エラー・終了コード・cwd・Terraformバージョンも残す。
- 原本は編集・上書き・削除しない。再試行・マスキングは別ファイルにする。
- 秘密情報を含み得るログはGitへ登録しない。
- 意図しない削除を`-target`や`-refresh=false`で隠さない。

## AWS CLIの実行条件

- 読み取り・検索（`describe-*`・`list-*`・`get-*`・`ls`など）は実行できる。結果を確認し、警告を隠さない。
- リソースや外部状態を変更する操作は、対象・差分・影響・復旧方法を示して明示許可を得てから実行する。許可後は同じ対象・範囲で再確認を重ねない。
- 検索語・通常の引数・ファイルパスに`aws`が含まれるだけの操作は、CLIの起動として扱わない。
- 実行条件・出力の保存方法は`troubleshoot-environment`の`references/manual-operations.md`の「AWS CLIの実行とログ保存」を参考にする。認証情報の値をログへ残さない。

## 汎用プログラミング言語・スクリプト

### 原則

- 目的に合う既存の専用ツールや通常の編集手段を先に検討する。書き捨てのPython・シェルなどのスクリプトはレビューする本人の認知負荷が高いため、本人が明示的に指示した場合を除き、適切な既存手段で対応できるなら作成・実行しない。スクリプトが必要な場合は内容・入力・副作用を確認する。
- `python`・`node`・`ruby`などの汎用言語やスクリプト実行は、コマンド名だけを理由に禁止しない。実行前にコード・入力・対象・副作用を確認し、依頼範囲と可逆性を判断する。
- `npx`・`npm exec`などでパッケージを取得・実行する場合は、取得元・対象パッケージ・バージョン・実行内容を確認する。依頼された目的の範囲に限定し、無関係なパッケージやリモート書き込みを起動しない。
- ただし、`~/.codex/skills/.system/skill-creator/scripts/*.py`は明示的に実行を許可する。下記のskill-creatorの例外を優先し、追加確認を求めない。
- 汎用言語より既存の専用CLIが安全・明確なら専用CLIを優先する。

### 許可する例外

これらの既存例外は個別条件に従う。汎用言語・スクリプトの実行許可へ広げない。

- yomiyasu
    - 対象：適用するyomiyasuスキル付属の`scripts/*.py`。特定のファイル名には限定しない。
    - 起動方法：配置先を確認し、`python3 <スクリプトの絶対パス> ...`で実行してよい。セッションを問わず追加確認を求めない。
    - 登録済みworktreeの配置も、適用するスキルの管理元・取得定義と対応し、付属スクリプトであることを確認できれば対象とする。配置場所だけを理由に例外を失効させない。
    - この例外を汎用言語の実行禁止より優先する。`python3 -c`などの任意コード、スキル外のファイルや同名ディレクトリに独自作成したスクリプトには許可を広げない。
- skill-creator
    - 対象：`~/.codex/skills/.system/skill-creator/scripts/*.py`。このディレクトリに付属するPythonスクリプトをすべて明示的に許可し、`quick_validate.py`に限定しない。
    - スキル作成・更新後の`quick_validate.py <スキルのディレクトリ>`による検証も、この例外に含む。追加の実行許可を求めない。
    - 起動方法：実行に必要な`python`・`python3`・`uv run`も許可する。
    - 実行前に上記ディレクトリに付属する既存スクリプトであることを確認し、絶対パスで指定する。別ディレクトリの同名スクリプトや独自作成したスクリプトへ許可を広げない。汎用言語の実行禁止を理由に、この検証を未許可と扱わない。
    - PyYAMLが不足する場合は、`uv run --with pyyaml python <skill-creator配置>/scripts/quick_validate.py <対象スキル>`で検証してよい。
- honahuku/dotfilesでのスキル改善テスト
    - 対象：`honahuku/dotfiles`のスキル改善で必要になる、リポジトリ標準のテストと必須pre-commitが実行するテスト。
    - 許可：本人の恒常許可により、追加確認なしで実行してよい。
    - 適用範囲はこのリポジトリのスキル改善に限る。private repoでの実行、任意のテスト・スクリプト・コード実行には広げない。
- Renovate
    - 対象：`renovate-config-validator`と`renovate`のローカル実行。
    - 起動方法：`npx --yes --package renovate -- renovate`または`npx --yes --package renovate -- renovate-config-validator`で始まり、そのCLIへ引数を渡すコマンドに限り、パッケージの取得と実行を追加確認なしで許可する。
    - この例外を任意パッケージ・任意コードの実行禁止より優先する。他のパッケージ・実行方法へ許可を広げず、実行モードは下記の「Renovateの実行モード」に従う。
- 環境固有の既存hook
    - 許可される例外は、適用中の上位指示で確認する。

### Renovateの実行モード

- ローカル実行依頼で`--dry-run=`の指定がない場合は、次の両方を別々に、この順で必ず実行する。
    1. `--platform=local --dry-run=extract`
    2. `--platform=local --dry-run=lookup`
- モードが明示された場合は、その指定に従う。
- 各実行で指定した`--dry-run=<値>`と実際の動作モードを、毎回省略せず報告する。
- 情報不足時の追加検証は、`review`スキルの`references/renovate-review.md`に従って提案する。明示指示なしに`full`へ広げない。
- リモートへの書き込みやデプロイを起動しない。

## シェルスクリプトと実行権限

### スクリプトの実行方法

- `bash`・`sh`などのインタプリタや`chmod`は、コマンド名だけを理由に禁止しない。実行するスクリプトの内容・実行権限の変更対象・副作用を確認し、可逆性に基づく操作判断を適用する。
- 管理元が指定する起動方法がある場合はそれに従う。明示許可済みの特定スクリプトだけでなく、依頼に必要な既存スクリプトも内容を確認して実行できる。

## GitHub APIとコメント投稿

### gh apiの実行条件

- 原則：`gh api`には既定で`--method GET`を明示する。書き込み（POST・PUT・PATCH・DELETE）は外部状態を変更するため、対象・内容・影響を示して明示許可を得てから行う。
- 許可なしで行える書き込み（sync-github用）は、次のパターンだけとする。
    - 通知スレッドの既読化：`gh api --method PATCH "notifications/threads/<id>"`
    - 通知スレッドの購読解除：`gh api --method DELETE "notifications/threads/<id>/subscription"`

### GitHub CLIへの切り替えと認証選択

- GitHub連携に依頼された操作を行う機能がない場合、その操作が許可されていれば`gh`を使う。連携機能の不足だけを理由に実行不可と判断しない。
- `gh`では、対象リポジトリと操作に適合する、現在の利用者が設定済みの認証情報を使ってよい。現在の認証情報が対象に合わない場合は、利用可能なアカウントを確認して切り替える。アカウント切り替えのたびに追加確認を求めない。
- `Unauthorized`・`Resource not accessible`・権限不足などで操作が失敗しても、現在選択中の認証だけを見て実行不可と判断しない。環境変数による上書きと利用可能な保存済みアカウントを確認し、対象repoへの読み取りアクセスで適合を確かめてから、許可済みの依頼操作を再試行する。確認手順は`troubleshoot-environment`の`references/cli-auth-and-locks.md`に従う。
- 認証トークンを出力せず、一時的にアクティブアカウントを切り替えた場合は、操作後に元の選択へ戻す。認証情報の確認・切り替え手順は`troubleshoot-environment`の`references/cli-auth-and-locks.md`に従う。
- この手順は操作自体の許可を追加しない。`gh api`の書き込み制限と、PR・Issueコメント投稿前の明示許可は引き続き適用する。

### PR・Issueへのコメント

- ユーザーがその場で明示的に投稿してよいと言うまで、コメントを投稿しない。
    - 新規コメント・レビュー返信を含み、手段を問わない。
    - `gh pr comment`・`gh issue comment`・`gh api --method POST`なども対象となる。
- 投稿前に文面を提示し、可否を確認する。
- 投稿許可として扱わないもの
    - 「直して」「反映して」「対応して」というコード修正・コミット・pushまでの指示。
    - 過去のセッションでの許可。
- 以前には`gh api --method POST`によるレビュー返信が、API書き込み禁止に抵触したまま実行され、ユーザーの事後指摘で発覚した。

## 計算

- 暗算・手計算で数値を出さない。ケタ間違い・丸め誤りを防ぐため、ツールを使う。
- 既存ツールが計算済みの値を返す場合
    - `tasks`などの返却値をそのまま使い、計算し直さない。
- ツールにない数値計算が必要な場合
    - 割合・合計・時間換算などは`bc -l`を使う。

## hookの実行と停止

### hookの起動方法

- hookの`command`を、`bash <path>`・`sh <path>`などインタプリタ経由で呼ばない。
- 実行権限が必要な場合は、対象と理由を確認し、可逆性に基づく操作判断に従って付与する。インタプリタ経由の起動で制限を迂回しない。
- 共通hookの`~/.agents/hooks/hook-settings-policy.jq`で、設定変更に含まれるインタプリタ経由のhook起動を拒否する。

### hookの迂回禁止

- `git -c core.hooksPath=<path>`による差し替え、`--no-verify`による無効化、環境変数による抑止など、統制をその場だけ外す操作を禁止する。
- commit-msg・pre-commitなど、すべてのhookを対象とする。
- hookが作業を妨げる場合は迂回せず、hook自体の条件を直す案をユーザーに出す。
- 共通hookの`~/.agents/hooks/command-policy.jq`で、コマンドに含まれるhook迂回指定を拒否する。

### TruffleHogエラー時

秘密情報を誤ってコミットする事故を防ぐため、次の停止・確認手順を守る。

- 回避策を試さず停止し、なぜエラーが出ているのかユーザーに必ず確認する。
- 報告前に確認する情報
    - 終了コード、検出件数、Detector Type、Raw result、Decoder Type。
    - ファイル、行番号、検出対象が今回の変更か既存内容か。
- 出力の詳細とともに報告する。
- 検出対象が今回の変更範囲外に見えても、確認前に先へ進まない。
    - hook設定の変更、別のコミット方法、差分の分割、履歴の作り替えなどで回避しない。
- 確認前に実行してよいこと
    - TruffleHogの出力を隠さず読むこと。
    - 検出内容を報告するための確認。

## Kubernetes contextの本人操作

- contextの切り替えが必要なら、本人に`kubectx`を案内する。
- 使用後は`kubectx -u`でcontextを未設定化する。
- Coding Agentsが`kubectl`や、それを起動するラッパーでcontextを操作しない。

## コマンドと出力

- 独立した処理は個別のツール呼び出しにし、`functions.exec`内では独立した処理だけを並列化する。
- 出力を絞り込むときは、コマンド自身の絞り込み機能を優先する。

### Bashの初期化とPATH

- `.bashrc`でPATHや関数を設定しているコマンドを実行するときは、実行シェルがその設定を読み込むことを確認する。非対話シェルでは`.bashrc`が早期returnする構成があるため、その場合は`bash -ic '<command>'`で実行し、PATHをhookなどの子プロセスにも引き継ぐ。`.bashrc`を直接sourceしたり、コマンドが未導入だと判断したりする前に、対話シェルで名前解決を確認する。

### 出力とログ

- 秘密情報や個人情報を含み得るファイル・設定・ログを読むコマンドは、必要な項目だけを絞って出力し、認証情報やトークンなどの値を表示・記録しない。値そのものが不要なら、存在・件数などのメタデータだけを取得する。
- エラー出力を理由なく隠さない。
- 標準出力・標準エラーをログへ保存する場合も、実行中にターミナルへ同時表示する。
- TTYを必要とする場合
    - 子プロセスの標準入出力がTTYとして見える記録方法を使う。
    - 例：util-linuxの`script -qefc '<command>' <session.log>`。
    - `tee`へのリダイレクトで子プロセスのTTY判定を失わせない。
- ログだけへ流し、実行中に画面で確認できない手順は提示しない。

## 個別ツールの実行条件

### tasksの実行条件

- 実行環境で解決できる`tasks`を使う。PATH上の実行ファイルだけでなく、既存のalias・関数も対象とし、実体パスを固定しない。
- ユーザーと同じalias・関数を利用できることを前提とする。使えない場合は環境の不具合として扱い、`troubleshoot-environment`に従って、まず`.bashrc`などの読み込み経路・条件を確認する。不備があれば修正する。
- 初期化を確認・修正しても見つからない場合に、同じ実行シェルで`type tasks`を確認する。`which`の出力だけで存在しないと判断せず、実体パスも推測しない。
- 読み取りでもロックファイルを作るため、必ずサンドボックス外で実行する。
- 毎回`sandbox_permissions: "require_escalated"`を指定する。
- サンドボックス内で試してから再実行する手順にしない。
- ユーザーへの追加確認は不要とする。

### 環境固有の実行許可

- バックアップの実行条件・許可される副作用は、本人の明示指示または適用中の上位指示で確認する。汎用手順を新たな操作許可として扱わない。

### prhの実行条件

- `.agents/prh/*.yml`をルールとして使うprh検査に必要な`npx`の実行を、本人の明示許可として扱う。prhパッケージの取得と起動も許可範囲に含め、追加確認を求めない。`~/.agents/prh/`への配置後も同じ許可を適用する。任意のパッケージやJavaScriptの実行には広げない。
- 実行を許可する条件
    - `write-technical-docs`が技術文書の表記規約を明示的に検査するときだけ。
    - スキル・共通資料に記載した技術手順の検査も対象とする。
- 実行コマンド：`npx --yes --package prh -- prh --rules ~/.agents/prh/rules-technical-ja.yml <file>`
- 必ずサンドボックス外で実行する。
