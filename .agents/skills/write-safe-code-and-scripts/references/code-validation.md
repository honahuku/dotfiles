# コード変更後の検証と警告の確認

## 手順(コードを書いた/編集した直後に毎回行う)

1. 該当言語の許可されたlintを実行し、後述の警告確認手順に従って指摘へ対応する。インフラ変更はCI確認も完了する
2. 許可されたfmt/formatterがあれば適用する。`terraform`・`kubectl`を伴うものは実行せずCI結果で確認する
3. 下表に従い、該当言語のGoogleスタイルガイド(https://github.com/google/styleguide)、またはDocker公式ベストプラクティスと照合する
4. t-wadaの発言「コードには How テストコードには What コミットログには Why コードコメントには Why not を書こう」を意識して、次を確認する。
   - コードのHow: 処理の実現方法を命名と構造で表し、コメントによる逐語的な説明に頼らない。
   - テストコードのWhat: 条件と期待する振る舞いをテスト名・入力・期待値で表す。実装手順をなぞるだけの検証にしない。
   - コードコメントのWhy not: 一見自然な代替案を採らない理由や、単純化すると壊れる制約を該当箇所に残す。コードから読めるHow・Whatは繰り返さず、根拠のない代替案や理由を作らない。
   - 設定項目を説明するコメントでは、正式な入力名を省略せず書く。「環境指定」や`environments:`への言い換えで、デプロイ先とSA選択の区別を曖昧にしない。短縮は明示的に許可された箇所だけに限定し、省略時・指定時・対象外の挙動を実装と照合する。
5. 実行可能なら実際に動かして確認する(テストがあればテストを実行する。シェルスクリプトは`chmod +x`が要るためユーザーに依頼した後、可能なタイミングで実行結果を確認する)
6. **nvim設定(Lua)を編集したら、毎回`nvim --headless`で起動し、エラー・メッセージの有無と変更箇所の状態を自分で確認してから提示する。** busted等のユニットテストは個別関数の検証であり、この手順の代わりにはならない。モジュール全体の読み込みエラー・キーマップ登録・autocmd登録の失敗はheadless起動でしか検出できないため、ユニットテストが通っていても必ず両方行う(2026-08-10、activity-bar機能追加でbustedのユニットテストだけ実行してcommitまで進み、headless起動確認を一度も行わなかった)。「見た目を確認して」と言われても実際の画面キャプチャはできないため、変更対象の値をluaevalやスクリプトで評価し、期待通りかを数値・文字列として確認することで代替する
   - 現在の公開dotfiles(`~/.config/nvim` → `~/git/honahuku/dotfiles/nvim`)を汚さず、編集中のworktreeの内容で検証するには、一時ディレクトリに`XDG_CONFIG_HOME/nvim`を編集中のworktreeの`nvim`ディレクトリへのsymlinkとして作り、`XDG_CONFIG_HOME=<tmp> nvim --headless -c 'qa'`でエラーの有無を確認する
   - 個別の値(ハイライト色・lualineコンポーネントの表示内容など)を確認したい場合は、確認用のLuaスクリプトをファイルに書き、`nvim --headless -c "lua dofile('<script>')"`で実行し、`print`した内容を読む(`-l <script>`はプラグインの初期化前に実行されるため使えない)
   - 確認が終わったら、一時ディレクトリ・確認用スクリプトは削除せず残してよい(スクラッチ領域に置く)
7. **nvim設定でシステムUIの文言(`vim.ui.select`/`vim.ui.input`のプロンプト・選択肢、`vim.notify`の通知文など)を書くときは、可能な限り日本語にする。** 英語のまま書かず、日本語で意味が通る文言に置き換える


## 警告を含む検査結果の確認

lint・テスト・hook・CIでは、終了コードと標準出力・標準エラーを合わせて確認する。終了コード0や成功表示は、Warningがないことを保証しない。

1. 出力を全件読み、Warningのルール名・ファイル・行・内容を確認する。出力が省略されていれば原本ログを取得し、未読部分を残して先へ進まない。
2. 各指摘を現在のコード・diffと照合し、今回追加したものか既存のものか、影響、修正するか残すかとその理由を判断する。既存という理由だけで無視せず、単純な誤りは修正する。リソース・依存バージョン・権限等の判断が必要なら確認する。
3. commit・push・完了報告の前に、全件の対応判断をタスクの記録か会話へ残す。同一ルール・同一対応の指摘はまとめてよいが、対象と件数を追える状態にする。新規または影響未評価の警告を、検査成功だけで許容しない。残す判断が承認済みの警告は、その状態を引き継ぐ。
4. 許可された`tflint --minimum-failure-severity=error`はWarningの表示を残し、Error以上で失敗させる。実行エラーも失敗として扱う。この設定でも上記の確認は省略しない。出力の破棄・Warningの非表示・`--force`や無断のルール無効化で通過させない。TruffleHogエラーと禁止CLIの結果不足は、AGENTS.mdの停止条件を優先する。


## 見つからない場合の扱い

lintツール・スタイルガイドが該当環境に無い場合は、無いままにせず確認する。「無いのでスキップする」という判断を勝手にしない。インフラ検証は上記のCI確認・停止条件を優先する。
