# ファイル編集と検証

- **成果物・ドキュメント・コードなど、ユーザーが手で編集している可能性があるファイルは、編集前に必ずReadで現在の内容を確認する。** system-reminderの「変更なし」は誤検知があるため過信しない

- 既存の成果物の修正・簡略化は、原則として元のパスを更新する。新規ファイルを作る前に同じ役割の既存ファイルを確認し、改訂のためだけに`-simple`・`-v2`・`-new`などの別ファイルを増やさない。別版の保持を明示された場合や、別用途として両方を維持する必要がある場合だけ分ける。保存が必要な実行ログ・証跡は対象外とする。

## コマンド・タスクの置換と統合

- 「AではなくBにする」「Aを廃止する」という指定では、旧コマンドの責務を移す範囲と、残してよい入口を確認する。BからAを呼ぶだけで置換済みとせず、旧定義・別名・呼び出し元も整理する。必要性や明示的な要望がない互換用の入口を残さない。
- 冪等な導入を求められた場合は、同じ到達状態を作る初回実行と再実行を同じ入口で扱う。再実行のためだけに復旧専用コマンドを追加・温存しない。固定版の取得と最新版への更新など、入力や到達状態の違いは冪等性の可否と分けて判断する。
- 完了前に、依頼された置換・廃止が定義、別名、呼び出し元、説明に反映されたか照合する。新しい入口の成功だけでなく、廃止した入口が実際のタスク一覧や設定の読み込み後にも残っていないことを確認する。

## コード編集
- コメントは、明示的な指示がなければファイル全体で日本語に統一する。複数人で変更しているファイルでは、既存コメントの言語・文体・書式に合わせる。識別子とツールが解釈する指示構文は保つ。外部取得物は上流の原文を維持する。
- 拡張子やGit管理の有無を問わず、作成・編集するテキストファイルは末尾改行で終える。空ファイルは許容する。末尾改行と末尾の空行を区別し、意図的な空行を検査警告だけを理由に削除しない。
- **t-wadaの発言「コードには How テストコードには What コミットログには Why コードコメントには Why not を書こう」を意識して、実装時とコミット前に必ず書き分けを確認する。** 具体的な確認は`write-safe-code-and-scripts`と`apply-git-strategy`に従う。出典: [Takuto Wadaの投稿](https://x.com/t_wada/status/904916106153828352)。
- TDD で進める。テストを先に書いてから実装する
- テストが通ってから次のステップに進む。テストが通らないまま実装を進めない
- 既存のテストを壊さない。リグレッションを出したら即修正する
- 言語ごとの Google スタイルガイド（https://github.com/google/styleguide）に準拠する
- 編集前に対象ファイルと既存差分を読む
- Git操作では、可能なら `git -C <path>` を使う
- **コード・スクリプトを新規作成・編集したら、提示前に自分でlint・fmt・スタイルガイド照合を済ませる。** 終了コード0やhook・CI成功だけで指摘なしと判断せず、出力のWarningも全件確認し、影響・対応判断を残す。検証用スクリプト・一時ツールも対象とし、詳細は`write-safe-code-and-scripts`の警告確認手順に従う。
- Terraform・Kubernetes manifestの編集・mergeによる取り込みでは、`write-safe-code-and-scripts`のインフラ検証手順を適用する。禁止コマンドを伴うfmt・検証をローカル実行せず、CI結果で確認する。
