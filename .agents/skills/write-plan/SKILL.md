# 実装計画を作る

## 作成

不要な長文や、説明済みの内容を複数箇所に繰り返し書くことは、依頼者だけでなくレビュアーや文書の読者の時間を奪う最低な行為である。読む・照合する・重複だと見分ける負担を相手に押し付けるため、単なる文体の好みとして扱わず、繰り返してはならない。
そのため、計画を書く前に既存の仕様・docs・議論を確認し、参照で足りる説明を写さず、この計画で決める内容と実装・検証に必要な情報を残す。提示前に`review-output`の「説明先をまたぐ重複チェック」を行う。

- 目的、対象範囲、対象外、前提、変更箇所、検証方法、未決事項を書く。
- 調査で分かった事実と、採用する設計判断を分ける。
- 実装者が追加判断を迫られる曖昧な表現を避ける。
- 既存コードのファイル、シンボル、設定名を確認して具体的に示す。
- 実装順ではなく、依存関係と検証可能な区切りで手順を組む。

## 着手前の確認

- 各手順に変更対象と確認方法があるか。
- エラー処理、互換性、移行、ロールバックが必要か。
- テストが正常系だけに偏っていないか。
- 外部仕様や数値を一次情報で確認したか。
- 未決事項を実装者へ暗黙に委ねていないか。

ユーザーが計画だけを求めている場合は、承認や追加指示を受けるまで実装しない。計画ファイルの保存やPR作成は、対象リポジトリの規則またはユーザーの依頼がある場合だけ行う。

## plan file のPR

- 保存先リポジトリと公開範囲を確認し、計画を複数のリポジトリへ重複保存しない。
- 保存・編集・反映の前に`apply-git-strategy`を適用する。作業場所と同期方法は`references/worktree.md`に従う。
- 計画だけのPRを通常のPRにするかdraftにするかは、保存先の規則に従う。非公開環境の具体的な保存先・例外は同名の非公開資料で確認する。
