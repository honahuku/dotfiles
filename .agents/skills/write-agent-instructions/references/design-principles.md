# 指示とスキルの設計資料

## 変更時の確認

### 編集前

1. 対象の規則と同じ役割の記述を検索し、管理元、参照元、実際の読み込み経路を確認する。廃止済みの指示や、同じ内容のコピーへ追記しない。
2. 各記述がどの判断・動作を変えるかを確認する。汎用的な能力の説明、コードから容易に分かる一覧、既存資料の言い換えだけなら追加しない。既存の安全制約や固有の検証条件を、一般論として削らない。
3. 次の表で置き場所を決める。公開できる手順を第一候補とし、社内・個人情報だけを既存の非公開資料へ分離する。処理に付随する設定・検査定義・テスト・ログも、下記の「処理とデータの公開可否」で個別に判断する。

| 内容                             | 管理元                                                 |
| -------------------------------- | ------------------------------------------------------ |
| 常時必要な短い制約・判断軸       | グローバルAGENTS.md                                    |
| 特定repo・ディレクトリだけの条件 | その範囲のAGENTS.md                                    |
| 特定作業の進め方                 | その作業を担当する既存スキル                           |
| 条件付きの詳細・例・仕様・背景   | スキルのreferencesまたは共通docs。入口に読む条件を置く |
| 機械的に判定する実行条件         | 対応するhook。共通指示の許可範囲内で検査する           |

### 編集中

- 各Markdown資料には内容全体を表すh1を一つ置き、その用途に対応するファイル名にする。SKILL.md・AGENTS.mdなど所定のファイル名は維持する。独立した用途が混在して長くなる資料は、読む条件ごとに分割する。改名する前に本文・設定・リンクの参照元を検索し、変更後に旧名の残存を確認する。

- `references/`の資料は、内容と用途がファイル名・見出しから分かるようにする。必須資料はスキル本文か関連する入口に、読む条件と相対パスを記す。後から追加される資料も共通指示の一覧確認で見つけられる構成にし、特定のファイル名を読込の条件にしない。

- 同じ規則の本文は一か所で管理する。呼び出し元には読むタイミング・参照先・作業固有の条件だけを残し、共通手順を再掲しない。OS別の環境資料にコミット命名規則を書くなど、資料の用途と無関係な規則が混ざっていないかも確認する。重複を統合するときは、管理元に固有の条件が残ることを照合してから参照へ置き換える。
- SKILL.mdには目的・共通の制約・作業の選択に必要な情報を残す。大きく異なるモードの詳細だけを分割し、短い自己完結したスキルへ不要な参照階層を増やさない。
- descriptionは主要な用途と起動条件を先頭に置き、本文の手順を詰め込まない。キーワードの数を増やすために対象外の作業まで拾う説明にしない。
- 例外は原則と別の文・箇条書きで示し、対象と条件を明記する。個別用途の条件を全作業へ広げない。
- 単純な作業に過剰な固定手順・全資料の読了・無関係な検査を課さない。正確性・安全性・許可に必要な必須手順は維持する。

### 完了前

- 移動・統合した規則について、変更前の対象・条件・例外・禁止・停止条件・必須検証が変更後のどこに残るかを照合する。正当な理由や許可がないまま弱めない。
- 通常の依頼、対象外の依頼、安全上停止すべき依頼で、選ばれるスキルと読む資料を確認する。対象外なら発火せず、必要な制約は操作前に読めることを確認する。
- 参照先の実在、循環参照、廃止した参照の残存、同名定義の重複、リンクの管理元を確認する。参照を追加するだけで古い本文を残さない。
- hookを変更した場合は、拒否すべき入力と許可すべき入力を確認する。設定の構文検査、実行経路の確認、実際のイベントによる検証を区別する。
- 行数・容量は肥大化の手がかりとして使い、短縮自体を完了条件にしない。未実施の起動確認や端末への未適用があれば、その範囲を報告する。

## 処理とデータの公開可否

公開可能な処理でも、その処理が参照するデータまで公開可能とは限らない。保存先はファイルの用途や実行場所ではなく、含まれる情報から決める。公開側を優先する方針は、非公開情報も公開側へ移す許可ではない。

1. 処理と入力データを分け、入力から作った設定・正規表現・テスト・期待値・ログ・説明例まで確認する。単体では目立たなくても、複数の記述を組み合わせて個人・会社・内部構成を推測できないか確認する。
2. 非公開にすべき情報が含まれる場合は、汎用処理だけを公開し、実際の値や定義は非公開側で管理する。公開側には値を含まない参照方法と、未配置・読込失敗時の動作を書く。安全性を検査する処理は、必要な定義が読めなければ成功扱いにしない。
3. 実在の値を正規表現・文字列分割・エスケープへ変えただけでは、匿名化したと判断しない。検査を通すために表記だけを変えず、公開先から情報を分離する。
4. 公開用のテストや例には、実在の値から作っていない架空の値を使う。実際の非公開データによる検証結果は、値が公開されない保存先で管理する。定義・入力・期待値・エラー表示を通じて非公開情報が戻っていないかも確認する。

| 例                                     | 公開側に置くもの                               | 非公開側に残すもの                         |
| -------------------------------------- | ---------------------------------------------- | ------------------------------------------ |
| 外部へ出してはいけない識別子を検出する | 検査処理、定義の読込方法、架空の値を使うテスト | 実際の識別子を含む禁止語パターンと検出ログ |
| 社内サービスへ接続する                 | 接続処理、設定形式、架空の接続先を使う例       | 実際の接続先・組織名・アカウント情報       |

例えば社内サービス名の一文字を文字クラスにした正規表現は、元の名前を読み取れるため公開用の架空データにはならない。

## 設計の根拠

仕様を判断する場合は、リンク先の現行内容と実際の実装を確認する。モデル固有の記事の推奨を、全モデル共通の制限や権限変更として扱わない。

AGENTS.mdは常時適用する制約と参照条件に絞る。作業固有の手順はスキルへ置き、複数モードの詳細は必要に応じて読む。広すぎるdescriptionや、毎回一式の資料を読ませる指定を避ける。[OpenAIのスキル・プロンプト見直し記事](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

descriptionの先頭に主要な用途と選択条件を短く書く。必要に応じて本文と補助資料が読み込まれるため、選択前のメタデータに全手順を詰め込まない。[OpenAIのSkillsガイド](https://learn.chatgpt.com/docs/build-skills)

グローバル設定には共通の規則を置き、プロジェクトやディレクトリに固有の条件は、その範囲の指示で扱う。実際の探索範囲・優先順位は使用するツールで確認する。[OpenAIのAGENTS.mdガイド](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

動作を変えない一般論や既存文書の複製を減らし、固有の例外と検証条件を残す。[AAIFのAGENTS.md執筆ガイド](https://aaif.io/blog/writing-an-effective-agents-md)

常時読む情報と、作業に応じて読むスキル・資料を分ける。[Red HatのAGENTS.mdとAgent Skills解説](https://developers.redhat.com/articles/2026/07/27/standardize-project-context-agentsmd-and-agent-skills)
