# エージェントの指示と起動条件

既存のAGENTS.md、スキル、hook設定と呼び出し元を確認する。同じ役割の定義があれば更新し、別名の重複を増やさない。機能追加でも文章の追記だけで終えず、変更する規則の適用範囲・既存の管理元・読み込み条件を先に決める。

## 編集前後の構成確認

AGENTS.md・スキル・Coding Agents向けhookを作成・編集する前と、その作業を完了する前に、`references/design-principles.md`の「変更時の確認」を適用する。小さな修正では、確認する資料を対象の規則と参照元に絞り、無関係な資料まで読まない。設計変更や公式仕様の確認が必要な場合は、同資料の出典を確認し、OpenAIの現行ガイドを優先する。推奨を、既存の禁止事項・承認境界を解除する根拠にしない。

## 呼称とツール固有の記述

Coding Agentsは、モデル・ツール・実行環境を組み合わせ、コードの調査・編集・テスト・修正を反復して開発作業を遂行するシステムを指す。LLMは言語モデル、AIは技術分野の総称であり、指す対象を区別する。

- 本人がAI・LLMと呼んでも、開発作業を遂行するシステムを指していればCoding Agentsと表現する。
- モデルそのものの説明、コード識別子、正式名称・出典は、意味を変える一括置換をしない。
- 判断基準・確認フロー・禁止事項の主語は、個別ツール名ではなくCoding Agentsにする。

Codex固有の名称・パスを記載する前に、次の順で確認する。

1. 共通表現で説明できないか確認する。
2. パスを指定する場合は、`.agents`へ置くか、`.agents`の管理元を参照できないか確認する。
3. 代替できない場合は、記載箇所、固有名が必要な理由、共通表現では説明できない理由を示す。パスでは共通配置・参照が使えない理由も示し、記載前に本人の許可を得る。
4. 許可された用途・範囲だけに記載する。既存の固有名を、新たな記載全般への許可と扱わない。

## 指示の置き場所

- AGENTS.mdには常時必要な短い禁止事項・判断軸と、条件別の参照案内を置く。
- 作業固有の手順はスキルへ、詳しい例・仕様・背景は必要なときに読む資料へ置く。複数スキルで使う操作手順は、その操作を担当するスキルの一か所に集約する。呼び出し元には、読むタイミング・参照先・その作業固有の条件だけを残す。固有の条件を全作業向けの規則へ広げない。
- 指示・背景・手順の配置は`docs/agents/context-policy.md`に従う。処理やデータを公開する前に、`references/design-principles.md`の「処理とデータの公開可否」を確認する。
- hookは機械的に判定できる条件を検査する。判断の理由・適用範囲は指示に残し、長い手順をhookから毎回コンテキストへ挿入しない。hookがあることを理由に、重要な禁止事項を指示から消さない。

## スキルの自動選択

スキル名とdescriptionは、本文を読む前に選択の手がかりになる。手動で名前を指定した場合だけ使える定義にしない。

- 名前は動作と対象が分かる英語にし、既存の命名規則に従う。
- descriptionに、実行する作業、対象ファイル・ツール、依頼で使われる言葉、作業前に読む必要がある条件を自然な文で含める。関係のないキーワードを並べない。
- 主要な作業と起動条件を短く先頭に書く。長い機能一覧や、無関係な作業まで拾う説明にしない。
- 類似スキルと区別する条件が必要なら記す。対象外の作業まで選ばれる広すぎる説明を避ける。
- 作業手順の途中で別のスキルが必要なら、呼び出し元の該当箇所に参照条件を置く。AGENTS.mdには全作業で必要な案内だけを残す。
- 自動選択を既定とする。明示呼び出し限定の指定は、本人が希望した場合だけ使う。スキルを選ぶことと、外部への書き込みなどの操作許可は分けて確認する。

スキルの作成・更新では、利用できる`skill-creator`を読み、定義の書式とメタデータを確認する。

## 言語・外部取得物・反映

自作スキルの説明文・参照文書は日本語にする。コード・識別子・正式な出典名は維持する。

`vendir.yml`と`vendir.lock.yml`の両方で管理される取得先は、禁止語・日本語検査と日本語化から除外し、上流の原文を保つ。自作の方針を直接書き足さない。秘密情報検査は引き続き適用する。

自作スキルの命名・仕様検査、変更したファイルのLefthookでの検査、mainへの反映後に行うリンク更新は`apply-git-strategy`に従う。リンク更新でファイルの削除や置換が必要なら、共通の本人操作手順を先に適用する。

## hookの作成と確認

hookは、対象ツールが対応するイベント・入力形式・実行方法を、既存設定と公式仕様で確認してから作る。descriptionによるスキルの選択と、イベントで実行されるhookを混同しない。

- どの操作の前後に、何を条件として実行するかを定義する。
- 対象に含める操作と除外する操作を確認し、禁止すべき入力の拒否と、許可された入力の通過を両方検証する。
- 実行権限・インタプリタ・禁止コマンド・秘密情報の扱いは共通の制約に従う。hookを無効化して検証を通さない。

## 反映前の確認

一般的なコーディング知識や、リポジトリから容易に確認できる一覧を重ねて書かない。具体的な制約・例外・判断に必要な手順を残す。複数の作業モードがあるスキルは、入口で該当資料へ案内し、一度に全資料を読ませない。

実際にあり得る依頼と、対象外の依頼を使い、スキルを選ぶ条件を照合する。参照先の実在、リンクの管理元、hook設定の読み込み経路も確認する。静的な定義の検査と、実際の起動確認を区別して報告する。

移動・統合した規則は変更前後で対応を確認し、対象・例外・禁止・停止条件が維持され、必要な操作より前に読まれることを確かめる。行数の減少や定義の構文検査だけで完了としない。
