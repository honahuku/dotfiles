環境固有の情報は`~/.agents/docs/work/context.md`の`review`セクションを参照する。対象業務で必要なセクションを取得できない場合、値や権限を推測せず停止する。

## 概要

PRの変更対象を理解し、図を使ったワークスルーと観点別の評価を示した上で、approve可否とコメント候補を提示する。コード、インフラ、ドキュメント、設計資料を対象とする。

ワークスルーは、社内で呼ばれるシステムと、そのシステムが任される役割を中心に組み立てる。ベンダーの製品名や内部の構成要素は、理解に必要な場合だけ補足する。対象システムを初めて知る読み手を前提にする。作図はMermaidを優先し、分かりやすさと作成時間を比較して手段を選ぶ。

## 実行手順

### 1. 対象PRと最新状態を読む

`$ARGUMENTS`からrepoとPRを特定する。番号がなければ`gh pr list`で候補を示して対象を聞く。

`gh pr view <N>`と`gh pr diff <N>`で本文、変更ファイル、CI状態、最新HEADを取得し、既存コメントとレビューも読む。大きな差分は責務やデータ経路ごとに読む。後で古い差分を評価しないよう、対象HEADを控える。`gh api`での取得には`--method GET`を明示する。

### 2. 変更対象のシステムを理解する

構成・責任・権限・依存関係の確認には`references/system-walkthrough.md`を使う。

この段階で[作図方針](references/visual-walkthrough.md)を読み、関係の整理に使う図と作成手段を選ぶ。

変数、module、共通設定、環境別の上書きや別repoの契約まで、今回の入出力と権限に関わる参照を追う。過去PRやIssueは、変更前の動きや設計判断がapprove可否に関わる場合に読む。worktreeが必要なら`apply-git-strategy`に従う。

社内での呼称、責務、実効権限を、repo名やベンダーの製品名から推測しない。設定に書かれた状態、planが示す予定、観測した実環境を区別する。docsとコードが食い違う場合は両方を示し、現在の運用を調べる。調査しても分からなかったことは、その項目と調査できた範囲を明記し、憶測で補わない。

### 3. 変更前後をたどり、観点別に評価する

変更前後の入力、処理、権限、出力を比較する。通常の処理に加え、今回の変更に関わる失敗時や適用途中の経路も追う。[レビュー観点と根拠](references/review-criteria.md)を読み、関係する観点について成立条件、影響、根拠を示す。確認して問題がない主要観点も、その理由を説明する。

Renovateによる依存更新PR、Renovate設定の変更PR、Renovateのローカル実行依頼では、[Renovateの検証・レビュー手順](references/renovate-review.md)を読む。依存更新の調査は依存更新PRに、ローカル実行の手順はローカル検証に適用する。

コードの主張は`file:path:line`で裏付ける。pathはrepo相対パス、lineは対象HEADの行番号とし、チャットでは同じ位置へのGitHubリンクかローカル絶対パスのリンクを添える。文書は該当ページやセクション、実環境は読み取り結果と対象環境を示す。Webの出典は本文を読んで主張との一致を確かめ、読めなければ根拠にしない。

検証は許可された静的検査とCI結果の読み取りに限る。Terraform・Kubernetes manifestでは`write-safe-code-and-scripts`のインフラ検証手順を読み、`terraform`・`kubectl`をローカル実行しない。必要な禁止CLIの結果を対象headのCIから取得できなければ、別の方法で代替せず判断を仰ぐ。適用・デプロイや、それを起動するmerge・push・CI操作は行わない。

CIで報告済みの整形・lint・型の問題は重複コメントにしない。ただし、未解決の不具合や必須CIの失敗は承認判断に残す。成功した検査のWarningも`write-safe-code-and-scripts`の警告確認手順で評価し、コメントの重複抑制を指摘の確認省略にしない。生成物は生成元との整合性や依存更新の影響を確認し、テスト用の例外は本番へ流入しないことを確かめる。

repoのAGENTS.md、設計要件、運用方針を一般的な推奨より優先する。共通AGENTS.mdの禁止事項は解除しない。次の既存運用も維持する。

ブランチ運用は、実際の反映方法を確認してから評価する。本番ブランチを自動追従する構成では、Helm valuesの`targetRevision: main` / `master`を固定タグへ変えることだけを理由に指摘しない。開発環境で検証ブランチへ切り替える構成では、ApplicationSetの`ignoreApplicationDifferences`で`targetRevision`を無視する設定を許容する。運用目的を確認し、本番・ステージング環境へ同じ例外を広げない。

対象リポジトリ固有のブランチ運用やレビュー基準は、非公開資料の`review`セクションで確認する。

### 4. 図でワークスルーを組み立てる

ステップ2で選んだ手段を使い、社内システムを主なコンポーネントとして、全体像と今回変わる箇所を可能な限り図で示す。ベンダーの製品名や構成要素は、権限の境界や変更の影響を説明するために必要な場合だけ、補足や詳細図に載せる。

図を先に示し、本文は図で伝わらない内容と根拠を補う。用語は初出で役割を説明し、識別子だけを並べない。未確認の関係を確認済みの構成として描かない。

提示前に、図と本文を合わせて次の内容が伝わるか確認する。

- 社内で何と呼ばれるシステムで、誰のために何を任されているか。
- 誰に、何のために、どの対象への操作権限が渡されているか。
- 上流・下流のシステムとどう依存し、どのデータや操作を受け渡すか。
- 今回解決する課題、変更する箇所、変更後の動きがどうつながるか。
- 誰にどのメリットがあり、どの条件でどんなリスクが生じ、どう対処するか。
- 調査しても分からなかったことと、説明・評価できる範囲はどこか。

ワークスルーの図と説明ができたら、最終応答に含める内容としてまとめ、ステップ5へ進む。一時応答には出さない。

### 5. approve可否を判断する

システム理解と観点別の評価から、現在のHEADについて判断する。[指摘の分類](references/review-comments.md)に照らし、必須修正と承認に必要な確認事項を特定する。

| 結論 | 条件 |
| --- | --- |
| approveできる | 要件と安全性を満たし、具体的な保守上の支障や承認に必要な未確認事項が残っていない |
| 要修正 | 修正必須の問題がある。満たすべき条件を示す |
| 判断保留（要確認） | 判断に必要な情報が不足している。不足情報と確認方法を示す |

任意の提案だけならapproveできる。必須修正が残る現在のHEADを、条件付きでapprove可能とは表現しない。情報不足を確認済みの不具合にせず、問題が見つからなかったことだけでapproveしない。

### 6. コメント候補を作り、選別する

[コメントの分類と書き方](references/review-comments.md)に従い、承認を妨げる問題と必要な確認事項をコメント化する。任意の提案は、利用者や将来の保守者の判断に役立つものだけ残す。ワークスルーの説明をすべてPRへの指摘に転用しない。

各候補にはPrefix、投稿先`file:path:line`、そのまま投稿できる本文を付ける。同じ原因の指摘はまとめ、`NITS`は最大5件にする。今回と無関係な既存課題、戦略や将来構想、根拠のない念のための質問は除く。

### 7. 最新状態を確認し、結果を提示する

最新HEAD、CI、既存コメントを再取得する。HEADが変わっていれば、影響する箇所の評価、図、approve判断を更新する。解決済みや重複の投稿候補は除く。既存コメントにある未解決の問題は、結論には含める。

最終応答では、変更範囲、ワークスルーの図と説明、変更前後、観点別の評価、approve判断、コメント候補をこの順に示す。観点別の評価は、今回の事実と根拠、評価、必要な修正または確認事項をつなげる。適用されない観点を機械的に埋めず、未検証と問題なしを区別する。

RenovateのPRでは、[依存更新の出力](references/renovate-review.md#結果に含めること)も変更前後の説明と観点別の評価に含める。

調査や作図の試行錯誤は結果に混ぜない。提示の末尾に「投稿しますか」「確認してください」などの承認を促す文は付けない。

### 8. 操作ごとの明示的な許可を確認する

レビューの説明・判断・文案作成と、GitHubへの操作は分ける。「コメントを考えて」「文面を作って」「approveしたい」は、文案や判断を求める依頼であり、投稿・approveの実行許可ではない。「問題ない」「LGTM」など内容への評価も操作許可にしない。投稿・approve・request changesは、それぞれの実行を明確に求める指示が必要であり、同じレビュー依頼のやりとりですでに明示されていれば、改めて確認する必要はない。

コメント投稿、approve、request changesは別々の操作として扱う。一つへの許可を別の操作へ広げない。approveレビューに本文を付けて送る場合は、approveとその本文投稿の両方が明示的に許可されていることを確認する。文案作成の依頼が含まれる場合、「投稿したい」「approveしたい」のような意向表明だけでは許可とみなさず、明示的な実行依頼がなければ文案と判断の提示で止める。依頼が曖昧な場合も投稿・レビュー送信を行わない。

投稿直前に最新HEAD、CI、既存コメントを再取得する。内容や投稿先が変わった場合は修正後の候補を示し直す。投稿には許可された`gh pr comment` / `gh pr review`を使い、`gh api`の書き込みで代替しない。
