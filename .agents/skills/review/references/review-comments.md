# コメントの分類と書き方

## 指摘を分類する

| 分類 | 判断基準 | Prefix |
| --- | --- | --- |
| 修正必須 | 今回の変更により要件違反、不具合、安全性の問題、具体的な保守上の支障が生じる根拠がある | `MUST` |
| 改善提案 | 現状でも要件を満たすが、別案に具体的な利点がある | `IMO` / `IMHO` / `NITS` |
| 確認質問 | 条件や参照先が未確認で、回答によって評価が変わる | `Q` |
| 指摘不要 | 好みだけ、今回の変更と無関係な既存課題、解決済み、既存コメントとの重複 | 候補から除く |

`FYI`は、対応不要でも将来の利用者や保守者の判断に役立つ事実に使う。`NITS`は軽微な表記や可読性の提案、`IMO`と`IMHO`は任意の設計案に使う。

好みだけの命名・整形でapproveを止めない。誤用や要件違反を招く命名・設定は、その影響で判断する。責務の混在、更新漏れを生む重複、検証不能な構造も、具体的な支障を示せるなら`MUST`になり得る。完璧さや想像上の将来要件を求めない。

`Q`には、何が未確認で、回答によってどの判断が変わるかを書く。承認に必要な質問と、任意の理解確認を区別する。情報不足を確認済みの不具合として`MUST`にしない。

## 本文を書く

人間向けには丁寧語で、コードと事実を対象に書く。1つの論点について、成立条件、影響、根拠を簡潔に示す。外部資料の一般論だけで今回の問題を断定しない。

`MUST`には必要な変更や満たすべき条件を書く。実装方法が複数あるなら1案を強制しない。`IMO` / `Q` / `FYI`は、レビュイーが判断できる仕様と帰結を示す。任意の提案には任意と明記し、修正指示の形にしない。

`suggestion`は原則付けない。直し方が明らかで1〜2行に収まる場合だけ付ける。文書の軽微な表現修正には短い書き換え案を添えてよい。根拠のリンクは主張の近くに置き、長い補足だけ`<details>`にまとめる。

仮想例として、VPN内に限定する要件があり、本番のSSH許可元が`0.0.0.0/0`になる差分なら、次のように書ける。

> MUST: この変更では本番のSSH許可元が全IPv4アドレスになります。VPN内に限定する要件と合わないため、指定されたCIDRに絞ってください。

本番での利用が未確認なら、条件を尋ねる。

> Q: この設定は本番にも適用されますか。SSH許可元をVPN内に限定する要件への影響を判断したいです。

## 投稿候補を選別する

承認の問題を解消するもの、または利用者や将来の保守者の判断を助けるものを残す。戦略や将来構想、今回と無関係な既存課題、根拠のない念のための質問は除く。既存コメントと重複する未解決の問題は結論には含め、新しい投稿候補は作らない。

同じ原因の指摘は1件にまとめ、Locationに該当箇所を列挙する。異なる影響や対処が必要な問題は別件にする。`NITS`は1回のレビューで最大5件とし、超過分は個別コメントにしない。必要なら同種の軽微な指摘が残ることだけ概要に記す。
