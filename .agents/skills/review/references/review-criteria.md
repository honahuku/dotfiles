# レビュー観点と根拠

今回の変更が要件を満たし、利用者と将来の保守者にどのような影響を与えるかを評価する。以下の判断基準は研究と実務指針を踏まえた運用方針であり、すべての変更に同じ項目や検証を要求するものではない。

## ソフトウェア全般

| 観点 | 今回の差分で確かめること | 指摘の根拠にするもの |
| --- | --- | --- |
| 正しさ・互換性 | 要件、境界値、未指定や空入力、失敗時の動作、既存呼び出し元への影響 | 仕様、呼び出し元、変更前後の処理、再現条件 |
| 安全性 | 認証・認可、テナント分離、外部入力、秘密情報や個人情報の出力 | 入力から操作までの経路、認可条件、ログやエラーの生成箇所 |
| 並行処理・状態 | 競合、重複実行、再試行、処理途中の失敗で生じる状態 | 操作順、共有状態、トランザクション、呼び出し側の再試行 |
| 設計・保守性 | 責務の境界、更新漏れを生む重複、不要な複雑さ、現在必要な機能との対応 | 既存設計、今回増える変更箇所、具体的な誤用・更新コスト |
| テスト・検証 | 変更した入力やデータ経路を検証し、不具合があれば失敗するか | テストの条件とassertion、差分への対応、必要なCIの結果 |
| 利用・運用・文書 | 利用方法、観測可能性、エラー時の対処、移行手順の整合 | README、運用手順、呼び出し側、ログ・監視設定 |

新規APIでは契約と認可を検証するテストを見る。DBアクセスは利用者やテナントの範囲、マイグレーションは新旧コードとの互換性と復旧への影響を確認する。例外を捨てる処理は、その後の結果と検知手段を調べる。ファイル名やテスト件数、CI成功だけから変更経路を検証済みとはしない。

性能やコストを指摘する場合は、入力規模、実行頻度、計算量、クォータなど今回の前提を示す。根拠のない高速化や、想像上の将来要件のための抽象化を要求しない。

保守性の悪化も修正必須になり得る。どの責務や検証を難しくし、どの変更時に支障が出るかを示す。等価な設計案が複数あるなら、著者の選択を好みだけで否定しない。軽微な磨き込みで改善全体を遅らせない。

## インフラで追加する観点

| 観点 | 今回の構成に照らして確かめること |
| --- | --- |
| 権限・公開範囲 | 誰が、何に、どの操作をできるか。用途に必要な範囲、認証・条件・継承、通信元と到達先 |
| データ・秘密情報 | 置換や削除の対象、データ保持・移行・復元、state / plan / ログの保存先とアクセス範囲 |
| 可用性・影響範囲 | 対象環境、共有リソースと依存利用者、停止・切り替え時の挙動、容量とクォータ |
| 適用順・復旧 | 依存するPRや基盤、設定と実体の対応、新旧構成の併存、必要な反映順、失敗時の回復手順 |
| 検知・運用 | 異常を識別するログ・メトリクス・通知、対応手順、運用主体が必要な情報と権限を持つか |

値の参照元、環境別の上書き、module、role、外部repoの契約まで追う。単一ファイルに危険そうな値があることだけで、実効権限や脆弱性の成立を断定しない。公開サービスや検証用設定など、要件と実行文脈によって判断が変わる。

TerraformではCIまたはHCP Terraformのrunのplanが示すchange・replace・destroyをコード差分と照合する。replaceの表示だけでデータ消失を断定せず、対象の性質、移行・復元手順、停止許容、依存先を確かめる。ユーザー判断が必要な影響は確認事項にする。必要なplan等を対象headのCIまたはHCP Terraformのrunから取得できない場合は、コードの目視や別の検査で代替せず停止して判断を仰ぐ。

レビュー用の予測planと後日作る適用用planは、環境の変化で差分が変わり得る。CI実行またはHCP Terraformのrun・対象環境・Git SHA・保存planとログを対応させ、過去の成功を最新差分の根拠にしない。リンクの提示は[plan結果の列挙](terraform-plan-results.md)に従う。[Terraformのplan仕様](https://developer.hashicorp.com/terraform/cli/commands/plan)を参照する。Coding AgentsはTerraform CLIを実行しない。

秘密情報はCLIで隠れていても、stateやplanに保存される場合がある。[Terraformの機密情報の扱い](https://developer.hashicorp.com/terraform/language/manage-sensitive-data)に照らし、保存と公開の経路を確認する。`create_before_destroy`は依存にも伝播し、同名リソースの併存制約もあるため、追加だけで無停止と判断しない。[lifecycleの仕様](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle)を対象リソースの制約と合わせて読む。

## 判断が分かれる例

- 広いロールを見つけた場合、必要操作と対象範囲を追う。要件を超える許可が成立するなら修正必須、文脈が不足するなら質問、同等に安全な別設計なら任意の提案にする。
- 重複した分岐は、見た目だけで修正必須にしない。認可規則の更新漏れなど具体的な支障を生む構造なら、その経路と根拠を示す。
- テスト欠落は、ファイルがないことだけで判断しない。変更した契約・経路・失敗条件を既存の検証が扱うか調べ、承認に必要な証拠の不足を特定する。
- 自動検査で報告済みの問題は重複コメントにしない。未解決の不具合や必須CIの失敗はapprove判断に残す。

## 研究と実務指針の位置付け

出典を追加する場合は、DOI付き査読論文やUSENIXなど大手学会の会議録、その他の論文、大手企業・OSSのレビュー指針、エンジニア向けカンファレンスの登壇資料の順で探す。論文は本文と対象・方法・限界を読み、製品の挙動は現行の公式仕様で確かめる。下位の資料を機械的にそろえる必要はない。

[BacchelliとBirdのICSE 2013論文](https://doi.org/10.1109/ICSE.2013.6606617)はMicrosoftでの調査から、レビューの成果に欠陥発見だけでなく理解、知識共有、改善があることを示す。コメントの分布を、個々の指摘を必須にする基準には使わない。

[RahmanほかのICSE 2019論文](https://doi.org/10.1109/ICSE.2019.00033)はPuppetを対象に、セキュリティ上の懸念を示すパターンと脆弱性を区別する。文脈によって評価が変わる知見を使い、件数や頻度をTerraformへ外挿しない。

[OpdebeeckほかのMSR 2023論文](https://doi.org/10.1109/MSR59073.2023.00079)はAnsibleを対象に、変数や処理がファイル・roleをまたぐ解析の必要性を示す。レビューでも参照先と実行条件を追う根拠にし、検出精度を他のIaCへ一般化しない。

実務の判断では、[Googleのレビュー基準](https://google.github.io/eng-practices/review/reviewer/standard.html)の保守性と改善を両立する考え方、[確認観点](https://google.github.io/eng-practices/review/reviewer/looking-for.html)の設計・機能・テストの評価、[コメント指針](https://google.github.io/eng-practices/review/reviewer/comments.html)の理由と必須度の明示を参考にする。これらはGoogleの指針であり、対象repoの要件と同一の義務とは扱わない。
